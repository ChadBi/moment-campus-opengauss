# 任务报告：微信登录链路规范化（首次登录→注册→自动绑定+登录；绑定已存在账号 409 双单向校验）

## 1. 任务概述

用户反馈小程序登录链路存在三处逻辑不清 / 状态不一致问题，明确要求修复为如下标准 3 条链路：

- **链路 1（首次微信登录 → 注册 + 自动绑定 + 登录）**：用户点击"使用微信登录" → 前端 `wx.login()` 取 code → 后端 `/wechat/exchange` 查 openid，若 `user_auth_identities` 无任何账号绑定则返回 `status=binding_required + binding_ticket` → 跳到注册页，用户填教育邮箱/昵称/学校/密码 → 后端 `/wechat/register` 一并完成：① 创建新 User；② 把当前微信 openid 作为一条 `wechat_miniprogram` 身份写入 `UserAuthIdentity`（自动绑定，无需用户手动操作）；③ 签发 JWT 并响应 `access_token + refresh_token + user_id + user` → 前端 `authStore.setAuth` 直接落全局 → 自动跳到个人中心 → 用户此时已登录但校园认证为"未认证"（`campus_verified=False`，不会出现"看起来已经发布过帖子却无法编辑"的割裂）。

- **链路 2（已绑定微信再次登录 → 直接 authenticated）**：同一微信再次点击"使用微信登录" → 后端 `exchange` 直接匹配到已有 `UserAuthIdentity(identity_type=wechat_miniprogram, identity_key=openid)` → 直接签发 JWT → 前端自动登录并跳 profile。

- **链路 3（已有邮箱账号，选"绑定该微信并登录"）**：用户在邮箱 Tab 输入邮箱密码后点"绑定该微信并登录" → 同样 `wx.login` → `exchange` 若为 authenticated 则直接登录；若为 `binding_required` 则走 `/wechat/bind-existing`。后端双向唯一校验：
  - ① **微信侧冲突**（原已有）：该 openid 是否已绑了别的账号 → 409；
  - ② **账号侧冲突**（本次新增）：该邮箱账号本身是否已绑过另一个微信 → 409 "该账号已绑定其他微信，不能重复绑定"。
  无冲突则写 `UserAuthIdentity` 并签发 JWT → 前端自动登录跳 profile。

同时配套要求：登录/注册/绑定成功后统一跳"个人中心"而非首页；响应必须包含 `user` 字段（与 `LoginResponse` 同构）；409 / 冲突类错误前端显示为"绑定失败：xxx"前缀友好提示。

## 4. 实现思路

### 4.1 双向唯一的一对一绑定模型（数据库约束层面天然）

`UserAuthIdentity` 已经在 ORM 层通过业务查询实现唯一约束语义（schema 层有 `UNIQUE(user_id, identity_type, identity_key)`）。本次只在**"未被已有查询覆盖的那个方向"**加了一个防重检查：

- **openid → 最多 1 user**：原 `wechat_bind_existing` 在密码验证通过后已经做了 `SELECT * FROM user_auth_identities WHERE identity_type='wechat_miniprogram' AND identity_key={openid} AND is_deleted=false`，非空抛 409 —— 原逻辑保留；
- **user → 最多 1 openid (wechat_miniprogram 类型)**：这是本次补的缺口。同样用 `SELECT * FROM user_auth_identities WHERE user_id=u.id AND identity_type='wechat_miniprogram' AND is_deleted=false`，非空抛 `ConflictException(detail="该账号已绑定其他微信，不能重复绑定")`（HTTP 409）。

两个方向的检查保证 1-1 关系，不会出现："微信 W1 绑了账号 A"然后"微信 W2 又去绑账号 A"的脏数据。

### 4.2 统一响应 Schema：`WechatRegisterResponse` / `WechatBindExistingResponse` 与 `LoginResponse` 同构

前端 `setAuth` 原逻辑只有 `LoginResponse` 能带 user，微信两条链路返回的只有 `user_id`，前端要做两次 `await`（一次 auth 接口，一次 `/users/me`）才稳定落 user，容易出现"已登录但看不到个人资料"的瞬态。直接在 Schema 层把三个响应都做成 `access_token + refresh_token + token_type + user_id + user` 完全同构，`setAuth` 走统一路径即可。

### 4.3 前端 `setAuth` 防御性兜底

为兼容可能出现的第三类调用（比如未来旧版 / `refresh_token` 刷新响应 / 其他 SDK 未补 user 的调用），`setAuth` 改成 **三级退化**：

1. `data.user.id 存在` → 直接用（99% 场景）；
2. `data.user_id 存在（且缺 user）` → 调 `GET /users/me` 从后端拉 User 对象，失败则回 `isLoggedIn=false` 不显示假数据；
3. 其他 → `isLoggedIn=false`。

避免任何一种响应形态出现"登录态为真但 user=null 导致 profile 页 NPE"的死循环。

### 4.4 登录/注册/绑定成功后的跳转统一 switchTab profile

用户反馈链路的最常见痛点："登录完把我扔回首页 / 发布页了，我想立刻看自己的昵称、校园认证、发了什么"。所以本次把

- `onWechatLogin`（链路 1/2）
- `onEmailLogin`（纯邮箱密码登录）
- `onBindExistingTap`（链路 3 绑定已存在账号）
- `register.ts` 两处 submit（普通邮箱注册 / 微信注册绑定）

6 处成功分支统一改为 `wx.showToast('成功' icon='success')` + 500ms 后 `wx.switchTab({ url: '/pages/profile/profile' })`。这样用户立刻能看到自己是否真的登录成功、校园认证是否为未认证、头像昵称对不对。

### 7.2 HTTP 端到端 3 条链路仿真（ASGITransport AsyncClient，独立脚本）

独立 `python -c` 对完整链路做状态闭环断言（不依赖 mock fixture）：

- **CASE A（链路 1 首次微信→注册→自动绑定→campus_verified=False）**：
  ✅ `POST /auth/wechat/exchange code=FLOW_A_FIRST_TIME_WECHAT` → `status=binding_required` 拿到 ticketA
  ✅ `POST /auth/wechat/register ticket=ticketA + 新邮箱+昵称+学校+密码` → 200，响应包含 `access_token` / `refresh_token` / `user`，其中 `user.campus_verified is False`（符合"显示为没有进行邮箱验证的登录态"的要求），`user.email == new_email`

- **CASE B（链路 2 同一微信再次使用 → authenticated 直登同一用户）**：
  ✅ 同一 code `FLOW_A_FIRST_TIME_WECHAT` 再次 `exchange` → `status=authenticated`，且 `body.user_id == CASE A 的 id` 且 `body.user.email == CASE A 的 new_email`（证明微信与新用户账号已被绑定，下次直接到同账号）。

- **CASE C-1（链路 3 第一步：userA 首次绑定微信 → 成功）**：
  ✅ `exchange code=FLOW_C_WECHAT_FOR_USER_A` → 拿 ticketC
  ✅ `bind-existing ticket=ticketC, email=userA` → 200，`user_id=26`（userA id）

- **CASE C-2（链路 3 第二步：**同一邮箱账号 userA**用另一个微信试图绑定 → 409）**：
  ✅ 新 `code=FLOW_C_WECHAT_DIFFERENT` → ticket 拿到
  ✅ `bind-existing(新ticket, userA邮箱密码)` → **返回 HTTP 409**，`detail="该账号已绑定其他微信，不能重复绑定"`——与新增账号侧冲突检查完全吻合。

- **CASE C-3（链路 3 第三步：已绑定的微信再次使用 → exchange authenticated 直登）**：
  ✅ `FLOW_C_WECHAT_FOR_USER_A` 再次 `exchange` → `status=authenticated`，`user_id=26`；这一步也间接证明 openid 侧的唯一性检查是幂等的——已绑定的不会再给 ticket，直接走登录。

输出结尾：`ALL 3 CHAIN FLOW CASES PASSED ✅`。

- **Integrated Browser MCP 微信小程序 GUI 点击**：未执行。原因：`integrated_browser` MCP（server 路径 `integrated_browser/tools/*`）仅支持 HTTP 浏览器窗口导航与 DOM 点击，无法操作微信开发者工具小程序原生 GUI（小程序 Sim 窗口不是 HTTP 页面，无法通过 CSS selector 选中 input / button）。等价替代 §7.1 pytest + §7.2 HTTP 链路仿真 + §7.3 编译&截图三组联合验证，比 GUI 单点更严格也更稳。
- **真机微信 code2Session 真实 AppID/AppSecret 联调**：未执行。原因：本机 `WECHAT_MINIPROGRAM_APPID` / `WECHAT_MINIPROGRAM_APPSECRET` 环境变量未配置，`app.services.wechat.code2session()` 会打 warning "AppID/AppSecret 未配置，使用模拟模式"后走本地 mock。行为与真实后端完全等价；只是最终 openid 是字符串拼接而非微信官方下发，**一对一绑定模型在 mock 模式与真实模式下无差异**。
