# 任务报告：注册阶段强制教育邮箱校验（B-01）

## 1. 任务概述

需求：用户在「注册阶段」必须使用所选学校对应的教育邮箱（或 @momentcampus.com 运营邮箱），防止使用 gmail/outlook 等非教育邮箱注册绕过「校园身份」语义。同时保留学校未配置任何 SchoolDomain（配置期极端场景）的逃生舱，避免系统自死锁。

覆盖两条注册链路：
- 邮箱注册：`POST /api/v1/auth/register`
- 微信注册：`POST /api/v1/auth/wechat/register`（同时删除原「空邮箱时生成 wx_xxx@momentcampus.local 临时邮箱」的逃生舱分支，B-01 后该路径必须强制教育邮箱）

## 4. 实现思路

采用 **统一 helper + 双接口调用** 的方案，好处是未来如果校园认证流程、资料修改邮箱等其他场景也需要同一套校验，可以直接 `from app.services.school_domain import ensure_email_matches_school_domains`，一处改动全局生效，避免多处复制逻辑产生漂移。

### `ensure_email_matches_school_domains` 6 条规则（按顺序判定）：

| # | 条件 | 行为 |
|---|---|---|
| 1 | require_email=True 且 email 为空/纯空白 | 400「请填写所选学校的教育邮箱」|
| 2 | email 不含 @ 或解析域名失败 | 400「请输入有效的邮箱地址」|
| 3 | 解析出的域名命中 `ALLOWED_NON_CAMPUS_DOMAINS`（momentcampus.com）| **return 放行**（运营账号如 admin@momentcampus.com 不需要受学校域名限制）|
| 4 | school_id 对应的 School 不存在或 is_active=False | 400「所选学校不存在」|
| 5 | 该校有 ≥1 条 SchoolDomain，但用户邮箱域名不在集合内 | 400 友好长提示：包含学校名、允许域名列表、运营邮箱说明、联系校管理员添加附加域名路径——一次性给出用户所有「如何解决此问题」的信息，而不是干巴巴的拒绝 |
| 6 | 该校未配置任何 SchoolDomain（配置期极端场景）| **return 放行**，保证刚搭建学校还没配置邮箱域名时，管理员/运营仍能注册首用户，不把系统锁死 |

### 为什么要求微信注册也必须填教育邮箱？

原链路支持「微信注册不传 email → 后端自动生成 `wx_xxx@momentcampus.local` 临时邮箱」。这在项目早期为了快速打通微信登录链路是合理的，但带来两个严重问题：
1. **用户账号没有有效邮箱**：后续找回密码、发校园认证验证码、接收互动通知等所有依赖邮箱的功能都会坏
2. **「校园身份」语义直接被穿透**：任何人都可以用微信注册，哪怕不是该校学生

B-01 后统一收口：无论邮箱注册还是微信注册，必须先拿学校教育邮箱当 ID 才能建立账号。

### 为什么 require_email 做成参数？

因为未来其他调用方（比如用户「编辑资料」改邮箱场景）也可能复用同一 helper，但编辑资料时允许用户不填邮箱（只改昵称/简介/头像），只有当用户**主动改邮箱字段**时才触发校验——所以设计成 `*, require_email=True` 关键字-only 参数，调用方语义显式（KW_ONLY 防止漏传）。

## 6. 影响范围

**模块级别影响**：
- `认证模块（auth/wechat_auth）` — 仅影响「新增用户注册」两个入口的邮箱校验前置，不影响既有已注册用户的登录、token 刷新、注销等任何其他操作
- `学校域名模块（school_domain）` — 首次抽成 service，后续校园认证 send/confirm 链路（目前 `users.py` 里是内联查询）可进一步收敛到此 helper，避免口径漂移（**留作后续优化项**，本任务不做以免影响范围膨胀）
- `测试工具链` — 自建临时学校的 helper 生成 code 的长度口径与 `School.code` varchar(20) 对齐

**前向兼容**：
- 已注册用户（包括早期用 gmail 注册的存量用户）**完全不受影响**——校验仅在「注册阶段」入口执行，登录/资料编辑等场景不受限
- @momentcampus.com 运营邮箱仍可注册为任意学校用户（豁免域放行），与 seed_data.py 中 `admin@momentcampus.com` / `fudan_admin@momentcampus.com` 等演示账号口径一致

**反向兼容**：
- 前端小程序 register 页已存在「选学校 → 邮箱 Input 显示对应学校 @xxx.edu.cn 后缀提示」的 UI 侧引导，后端加硬校验后与前端语义对齐，不再是前端仅提示但后端放行的"软建议"

## 8. 后续建议

1. **`users.py::send_campus_verify` 里的域名校验内联查询收敛到 helper**：当前 `app/api/users.py` L128-137 仍是手写的 `email.rsplit("@",1)[-1].lower()` + `SELECT SchoolDomain` 单独内联查询，与本 helper 语义等价但实现不同——未来可重构为 `ensure_email_matches_school_domains(db, current_user.school_id, current_user.email, require_email=True)`，一处改动全局生效（注意 campus_verify 报错文案是"邮箱域名与您的学校不匹配，请使用学校官方邮箱注册/登录"，与注册阶段 400 的长文案略有不同，可以在 helper 新增一个 `error_context` 参数或覆盖文案参数，避免统一后语义走样）。
2. **前端小程序 register 页面的「邮箱域名动态 placeholder」**：当用户选择江南大学（配置了 @jiangnan.edu.cn / @stu.jiangnan.edu.cn / @example.jiangnan.edu.cn）时，邮箱 Input 的 placeholder 可以直接显示默认后缀 `@example.jiangnan.edu.cn`，同时做一个轻量的 onBlur 校验：如果用户填了 gmail 等非校域名，在前端即时红字提示「请使用江南大学官方教育邮箱：@ jiangnan.edu.cn / @ stu.jiangnan.edu.cn / @ example.jiangnan.edu.cn」，减少用户填完再被后端 400 拦的往返体验损耗。
3. **运营邮箱注册时的角色与风险提示**：命中豁免域 @momentcampus.com 注册成功后，可以在后台 Admin 视角加一个"非校园邮箱注册用户"的小徽标——运营账号虽然功能与普通用户相同，但管理员视角一眼就能识别"这是平台运营小号"，降低后续多租户跨校权限审计时把运营号误当学生号的沟通成本。
4. **异常监控埋点**：为 helper 每次触发 400 拦截记录结构化日志（学校 ID、用户提交的邮箱域名、命中哪条规则的 400），可以作为后续「哪些学校的学生邮箱域名配置不全」的数据驱动依据——比如某天发现浙大校 100 条注册拦截都集中在 `@zju.edu.cn` 之外的 `@cs.zju.edu.cn`（计算机学院专属后缀），那就知道应该联系浙大校管理员加 `cs.zju.edu.cn` 附加域名了。
