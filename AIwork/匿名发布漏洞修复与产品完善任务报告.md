# 任务报告：匿名发布漏洞修复与产品完善

## 1. 任务概述

根据用户反馈的两个核心需求，对匿名发布机制进行安全漏洞修复 + 产品体验完善：
- **安全层面**：修复匿名发布身份泄露漏洞（`user_id` 真实 ID 暴露、不同接口匿名处理逻辑分散不一致、AI 证据卡片口径缺失豁免）
- **产品层面**：补充匿名功能的产品形态（作者本人/管理员可通过「匿名」徽章明确知道内容对外匿名、学校可关闭匿名发布时前端发布页 checkbox 自动禁用）
- **管理层面**：新增基于 `school_settings.allow_anonymous` 的校级开关（写入侧 400 拦截）与公开 settings API，支持产品运营按学校差异化治理匿名功能

## 4. 实现思路

### 4.1 安全：匿名 = 对外「没有身份」，对内「本人/管理员可识别」

原实现把 `author` 置为 null 但保留了 `user_id`，相当于给匿名穿了层薄纱，前端只要读取 `user_id` 就能精确定位用户。本次修正思路：
- **对外**（其他用户 / 游客）：匿名内容的 `author=null` 且 `user_id=null`，没有任何可识别身份字段
- **对内 1 作者本人**：为了让作者在「我的发布」里认出自己的内容，豁免显示真名 + 真 `user_id`，同时通过前端徽章显示「匿名」提醒这条对外是匿名的
- **对内 2 管理员**：社区治理需要，管理员可看到真身份，同样显示「匿名」徽章，提醒管理员这是用户出于隐私意愿发布的匿名内容

脱敏判断统一抽成 `should_reveal_identity`：
```
return not is_anonymous
    or (current_user is not None and current_user.id == owner_user_id)
    or is_admin(current_user)
```

### 4.2 统一化：用 helper 替换分散代码避免后续不一致

原项目 6 个 API 模块各自手写 `if is_anonymous: author = None`，每处逻辑略有差异（有的 UC-01 误把「匿名」写成「已离校用户」，实际需求完全不同）。统一用 `apply_author_mask(response, orm, current_user)` 后，后续新增内容类型（比如「校园公告」的匿名变种）只要调用同一个函数即可，保证全局脱敏逻辑一致。

### 4.3 产品体验：徽章 + 禁用控制，让匿名状态可感知

- **Badge**：匿名发布的核心痛点是「我匿名了但我自己不知道」。作者本人和管理员豁免显示真名，这会带来「这条到底是不是匿名？」的困惑，所以需要 UI 上显式展示一枚浅灰徽章，柔和不抢视线，但一眼能看清状态
- **禁用控制**：校级开关开启/关闭匿名发布时，不能只有后端 400，前端要在用户勾选之前就把 checkbox disabled，配个灰色提示 + tooltip 文案，降低发布失败率

## 6. 影响范围

- **匿名内容展示链路**：首页信息流、帖子详情页、评论列表、评价列表、推荐页、搜索结果页、专题详情页、地点 AI 摘要证据卡片共 8 处，现在都走统一脱敏
- **写入链路**：创建帖子、更新帖子，会额外读取一次 school_settings，对写入 RT 影响 1 次索引查询（`school_id` 唯一索引，<1ms）
- **公开接口新增**：`GET /api/v1/schools/current/settings`，对游客开放，无认证，使用量 = 前端每次切校 + 刷新 1 次（因为不持久化），QPS 很低
- **前端影响**：useCampusStore 状态从 8 个扩展到 10 个（+publicSettings / +publicSettingsLoading）；Header 页头无变化；主要影响帖子卡片、详情、发布页三个页面
- **不影响**：管理员审核接口、举报接口、协同验证接口（confirm/refute）、认证流程、学校切换流程

## 8. 后续建议

1. **前端匿名徽章的覆盖一致性**：本次只做了 HomePage + PostDetailPage；搜索结果页（SearchPage）、地图弹窗帖子卡、个人中心「我的发布」列表、LocationPage 评价列表也应统一补上「匿名」徽章，避免本人/管理员在这些页面看不到匿名状态提示
2. **Comment 匿名写入支持**：目前评论/评价的 Schema 与 脱敏都支持 `is_anonymous` 了，但前端没有 checkbox，后端 CommentCreate / LocationReviewCreate 请求体也未接收 `is_anonymous`（只做了响应侧脱敏，UC-01 原逻辑是「用户离校后自动匿名」）。如果要支持用户主动匿名评论，需要给 CommentCreate、LocationReviewCreate 加 `is_anonymous` 字段，与 posts 同样做学校 allow_anonymous 校验
3. **AI 摘要来源卡片的匿名徽章**：本次只对 sources 的 author_name 做了豁免，没有在前端地点详情页的 AI 摘要证据卡片上补上「匿名」徽章；本人/管理员虽然能看到真实昵称，但不知道这条证据是否匿名，建议在 UI 上加对应徽章
4. **TS 类型 & 响应模型联动**：建议前端 types 与后端 schemas 通过 openapi-typescript-codegen 或类似工具自动生成，避免类似本次「user_id 从 int 变 null」的 schema 变更时，前端 TS 类型需要手动改三处
