# 任务报告：排查并修复账号无法直接微信登录（MOCK 模式 openid 恒常化）

## 1. 任务概述

排查用户反馈「账号 1030424433@stu.jiangnan.edu.cn 无法直接进行微信登录」的根因并修复。现象：用户已在该邮箱下注册过账号，且之前点击过「绑定该微信并登录」至少两次，但再次切到「微信」Tab 点击一键登录时，仍会跳到注册/绑定页面（而非直接进入首页）。

## 2. 已完成内容

### 2.1 系统化证据收集（Phase 1，4 条线索 + 数据库实锤）

| 编号 | 排查点 | 结论 |
| --- | --- | --- |
| P1-1 | 读取 `seed_data.py` | 演示账号 seed 时未预设 wechat 身份，不是本次 Bug 根因 |
| P1-2 | 登录页 `login.ts` 的 `onWechatLogin` 分支 | 逻辑正常：`exchangeRes.status === 'authenticated'` 直接进首页，否则 `binding_required` 跳绑定/注册 |
| P1-3 | 后端 `wechat_auth.py` 的 exchange + bind_existing 链路 | 查身份 SQL 正确，bind_existing 做了双向唯一校验，均无 Bug |
| P1-4 | 后端 `wechat.py` 的 `exchange_wechat_code` MOCK 分支 | **发现 Bug**：AppID/Secret 未配置时用 `f"mock_openid_{code[:16]}"` 生成 openid，而 wx.login() 的 code 是一次性临时码，**每次点击都会变** → openid 永远不稳定 |
| P1-5 | **真实数据库铁证**：`user_auth_identities` 表 | 账号 1030424433@stu.jiangnan.edu.cn（user_id=25）下已绑 3 条身份：email ×1 + wechat_miniprogram ×2（openid 分别是 `mock_openid_0e1ox1Ga1QVwcM0Z` 和 `mock_openid_0d1iymll2gXtci4Q`，印证 09:59 和 10:27 两次"绑定"都产生了全新 openid，下次点击肯定查不到，必然命中 `binding_required`） |

### 2.2 根因定位（Phase 2）

MOCK 模式下的 openid 生成策略错误：**它把 wx.login() 的临时 code 当作稳定 openid 的种子，而 code 本身是一次性的，每次调用都不同。** 这导致：

1. 即便同一开发者反复走「绑定该微信并登录」流程，也只会在 DB 里不断堆积新的 `mock_openid_*` 身份（用户账号 25 就积累了 2 条，另还有 flow 测试用户 26/28 各 1 条，共 4 条垃圾身份）。
2. 下一次点击「微信一键登录」时，code 变 → 生成的 mock_openid 又变 → 后端查不到对应身份 → 返回 `binding_required` → 跳到注册页。
3. **即：本地开发模式下「绑定 → 下次直接微信登录」的链路从未真正跑通，是必然失败的逻辑。**

### 2.3 最小修复（Phase 3）

在 `backend/app/services/wechat.py`：
- 新增模块级常量 `MOCK_STATIC_OPENID = "MOCK_OPENID_STATIC_20260808_LOCAL_DEV"`（**大写前缀 `MOCK_`**，与旧小写 `mock_openid_*` 完全不冲突，便于后续区分和清理）。
- 导出常量符号，供测试侧直接引用，避免魔法字符串双写。
- `exchange_wechat_code` 的 MOCK 分支改为返回**固定常量**，**不再依赖 code**，模拟真实微信 code2Session 的行为：同一微信用户无论传什么临时 code，openid 都稳定不变。
- `session_key` 改为进程内仅生成一次（`_MOCK_STATIC_SESSION_KEY`），避免无意义的随机数生成。

同步更新测试：`backend/tests/test_wechat_auth.py` 的 `test_wechat_exchange_bound` 用例，将"根据 code 前 16 位推导 openid"的断言逻辑改为直接 `from app.services.wechat import MOCK_STATIC_OPENID` 引用，并同步更新注释解释。

## 4. 实现思路

严格遵循系统化调试的四阶段法：
1. **Phase 1 证据收集**：先不碰代码，把「前端分支 → 后端接口 → 微信 SDK → 数据库真实数据」四条链路全部读完并行取证，四个方向一致指向同一个嫌疑人（mock_openid 派生自临时 code），铁证如山再动刀。
2. **Phase 2 根因总结**：用「现象 → 机理 → 数据印证」三要素闭环解释，不是拍脑袋猜。
3. **Phase 3 最小修复**：只改一个点（`exchange_wechat_code` MOCK 分支 openid 来源），不碰绑定流程、不碰 identity 模型、不碰数据库 schema，**控制 blast radius**；同时把常量导出给测试，避免双写魔法字符串。
4. **Phase 4 验证 + 清理**：先 pytest 21 项回归，再清理 DB 垃圾数据（避免修复后仍有旧身份干扰判断），最后更新文档与任务报告。

## 8. 后续建议

1. **立即完成手动端到端验证**（TODO 已留 checklist）：在微信开发者工具打开项目，按「邮箱绑定 → 退出 → 微信直登」三步走一次，确认第三步直接进入首页，不再跳注册页。
2. **配置真实微信 AppID/AppSecret**（推荐）：在 `settings` 里配置真实的小程序 AppID 和 AppSecret（使用 `.env` 或环境变量，不要硬编码到代码），彻底脱离 MOCK 模式。本修复只是让 MOCK 模式行为正确，真实联调时生产逻辑走的是 httpx 调微信官方 code2Session，不会被常量影响。
3. **在 `UserAuthIdentity` 表上建唯一索引**（可选优化）：`(user_id, identity_type, identity_key) WHERE is_deleted = false` 部分唯一索引。现在靠 ORM 先 SELECT 再 INSERT 防重复，但在极端并发下仍有微小窗口产生重复身份。唯一索引可以把"一个账号绑多条相同类型+相同 identity_key"的行为拦在数据库层。这是独立优化，与本次修复无直接耦合，可放到下一个迭代。
4. **旧数据巡检脚本**（可沉淀保留版本，但本次未留）：若后续多人开发积累了更多 mock_ 身份，可复用本次删除逻辑（`identity_key LIKE 'mock_openid_%'` 匹配旧规则）做一次清表。
