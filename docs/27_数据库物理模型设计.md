## 1. 物理模型设计概述

### 1.1 设计目标

将 [doc 26 逻辑模型](docs/26_数据库逻辑模型设计.md) 中定义的 21 张关系模式与 15 个视图，落实为 **openGauss 7.0.0-RC3 轻量版**上的物理存储结构，重点解决：

1. **存储结构**：表空间划分、存储参数、字段类型物理实现
2. **访问性能**：索引设计、物化视图、查询优化
3. **业务自动化**：存储过程、触发器、定时任务
4. **数据治理**：分区、归档、清理策略
5. **openGauss 特性应用**：行存/列存、Ustore/Astore、增量检查点

### 1.2 设计原则

| 原则 | 说明 |
| ---- | ---- |
| 业务匹配 | OLTP 为主（信息发布、评论、点赞），含少量 OLAP（管理员仪表盘） |
| 读写均衡 | 读多写多，索引需兼顾查询与写入开销 |
| 分区友好 | 大表（posts、comments、notifications）按时间或状态分区 |
| 可维护性 | 物理对象命名规范、注释完整、变更可追溯 |
| 可演进性 | 索引/分区/存储过程可在不改逻辑模型的前提下独立演进 |

### 1.3 目标数据库特性

| 存储引擎 | Astore（默认）+ Ustore（关键表） | Astore 适合读多写少，Ustore 支持原地更新 |

## 2. 物理存储结构设计

### 2.1 表空间设计

openGauss 通过表空间（Tablespace）将物理存储与逻辑 schema 解耦，便于按访问模式分离 I/O。本项目设计 4 个表空间：

```sql
-- 2.1.1 系统表空间（默认）
CREATE TABLESPACE ts_system
    OWNER gaussdb
    LOCATION '/var/lib/opengauss/data/system';

-- 2.1.2 业务核心表空间（posts / users / validation_records）
CREATE TABLESPACE ts_core
    OWNER gaussdb
    LOCATION '/var/lib/opengauss/data/core';

-- 2.1.3 互动表空间（comments / likes / favorites / notifications）
CREATE TABLESPACE ts_interaction
    OWNER gaussdb
    LOCATION '/var/lib/opengauss/data/interaction';

-- 2.1.4 日志与历史表空间（admin_operation_logs / browse_histories / search_histories）
CREATE TABLESPACE ts_log
    OWNER gaussdb
    LOCATION '/var/lib/opengauss/data/log';
```

**表空间分配策略**：

| 表空间 | 物理路径 | 存放表 | 访问特征 |
| ------ | -------- | ------ | -------- |
| ts_system | /data/system | schools / categories / post_types / tags / locations | 配置类，读写比 ≈ 100:1 |
| ts_core | /data/core | users / posts / post_tags / post_images / validation_records / reports / drafts / topic_collections / topic_collection_posts | 核心业务，读写均衡 |
| ts_interaction | /data/interaction | comments / likes / favorites / notifications | 高并发写入，热点数据 |
| ts_log | /data/log | admin_operation_logs / browse_histories / search_histories | 仅追加，定期归档 |

### 2.2 存储引擎选择

openGauss 支持两种存储引擎：

| 存储引擎 | 适用场景 | 本项目选用 |
| -------- | -------- | ---------- |
| Astore（追加存储） | 读多写少、历史数据、批量查询 | posts、validation_records、histories、logs |
| Ustore（原地更新） | 高频更新、热点行、需 NUMA 优化 | users、comments、likes、notifications |

```sql
-- 指定存储引擎示例
CREATE TABLE posts (
    -- 字段定义见 doc 26
) WITH (
    ORIENTATION = ROW,
    STORAGE_TYPE = USTORE,
    COMPRESSION = MIDDLE
);
```

### 2.3 字段类型物理映射

将逻辑模型中的抽象类型映射为 openGauss 物理类型：

| 逻辑类型 | openGauss 物理类型 | 字节数 | 说明 |
| -------- | ------------------ | ------ | ---- |
| BIGINT | BIGINT | 8 | 主键、外键（统一 BigInteger） |
| INTEGER | INTEGER | 4 | 计数类字段 |
| VARCHAR(n) | VARCHAR(n) | 变长 | 字符串，n 为最大字节数 |
| TEXT | TEXT | 变长 | 长文本（content、detail） |
| BOOLEAN | BOOLEAN | 1 | 状态标志 |
| NUMERIC(10,7) | NUMERIC(10,7) | 8 | 经纬度（精度 7 位小数 ≈ 1cm） |
| TIMESTAMP | TIMESTAMP WITH TIME ZONE | 8 | 带时区的时间戳 |
| BLOB | BYTEA | 变长 | 二进制数据（本项目不用，图片走对象存储） |

**关键说明**：
- 原 SQLite 项目中主键为 Integer、外键为 BigInteger，存在类型不一致问题。物理模型统一为 BIGINT（详见 [doc 20 openGauss 适配分析 H1](docs/20_openGauss适配分析.md)）。
- `created_at`、`updated_at` 使用 `TIMESTAMP WITH TIME ZONE`，避免时区歧义。
- `password_hash` 使用 `VARCHAR(255)`，兼容 bcrypt 输出。

### 2.4 存储参数设计

针对不同访问模式的表设置 openGauss 存储参数：

```sql
-- 2.4.1 核心业务表（高频读写）
CREATE TABLE posts (...) WITH (
    ORIENTATION = ROW,
    STORAGE_TYPE = USTORE,
    COMPRESSION = MIDDLE,
    FILLFACTOR = 80,              -- 预留 20% 空间用于 UPDATE
    INITRANS = 10,                -- 高并发事务槽
    MAXRANS = 100
);

-- 2.4.2 互动表（高并发写入）
CREATE TABLE likes (...) WITH (
    ORIENTATION = ROW,
    STORAGE_TYPE = USTORE,
    FILLFACTOR = 90,
    INITRANS = 20
);

-- 2.4.3 日志表（仅追加）
CREATE TABLE admin_operation_logs (...) WITH (
    ORIENTATION = COLUMN,          -- 列存，压缩比高
    COMPRESSION = HIGH,
    FILLFACTOR = 100
);
```

| 参数 | posts | users | comments | likes | logs | 说明 |
| ---- | ----- | ----- | -------- | ----- | ---- | ---- |
| ORIENTATION | ROW | ROW | ROW | ROW | COLUMN | 列存适合扫描 |
| STORAGE_TYPE | USTORE | USTORE | USTORE | USTORE | ASTORE | 日志不更新 |
| COMPRESSION | MIDDLE | LOW | MIDDLE | LOW | HIGH | 日志压缩收益大 |
| FILLFACTOR | 80 | 80 | 85 | 90 | 100 | 高更新预留空间 |
| INITRANS | 10 | 10 | 15 | 20 | 4 | 并发事务槽 |

## 3. 索引设计

### 3.1 索引设计原则

1. **主键自动建索引**：openGauss 自动为 PRIMARY KEY 创建 B-tree 索引
2. **外键建索引**：所有外键字段建立索引，加速 JOIN 与级联操作
3. **高频查询条件建索引**：依据 doc 24 数据流图中的处理过程识别查询模式
4. **复合索引遵循最左前缀**：将等值条件放前、范围条件放后
5. **避免过度索引**：每个索引都会增加写入开销，控制在每表 5-8 个索引

## 4. 存储过程设计

### 4.1 设计原则

将业务逻辑中高频、复杂、需保证原子性的操作封装为存储过程：

1. **可信度计算**：验证记录提交后自动重算信息可信度
2. **过期检查**：定时扫描过期信息并更新状态
3. **冲突检测**：同地点同时段多条矛盾信息时自动标记冲突
4. **信誉分更新**：用户验证行为对其信誉分的影响
5. **数据归档**：日志与历史数据的定期归档

### 4.2 存储过程清单

| 存储过程 | 名称 | 触发方式 | 功能 |
| -------- | ---- | -------- | ---- |
| SP01 | sp_recalc_credibility | 触发器调用 | 重算信息可信度 |
| SP02 | sp_mark_expired_posts | 定时任务（每小时） | 标记过期信息 |
| SP03 | sp_detect_conflict | 触发器调用 | 检测同地点矛盾信息 |
| SP04 | sp_update_reputation | 触发器调用 | 更新用户信誉分 |
| SP05 | sp_archive_logs | 定时任务（每日） | 归档历史日志 |
| SP06 | sp_cleanup_soft_deleted | 定时任务（每周） | 清理过期软删除数据 |
| SP07 | sp_publish_post | 应用层调用 | 信息发布流程（状态校验+计数更新） |
| SP08 | sp_submit_validation | 应用层调用 | 提交协同验证（原子操作） |

### 4.3 存储过程详细定义

#### 4.3.1 SP01 sp_recalc_credibility（重算信息可信度）

```sql
CREATE OR REPLACE FUNCTION sp_recalc_credibility(p_post_id BIGINT)
RETURNS NUMERIC(5,2) AS $$
DECLARE
    v_confirm_cnt   INTEGER;
    v_refute_cnt    INTEGER;
    v_update_cnt    INTEGER;
    v_expire_cnt    INTEGER;
    v_conflict_cnt  INTEGER;
    v_credibility   NUMERIC(5,2);
    v_author_rep    NUMERIC(5,2);
BEGIN
    -- 统计 5 类验证记录
    SELECT
        COUNT(*) FILTER (WHERE validation_type = 'confirmation'),
        COUNT(*) FILTER (WHERE validation_type = 'refutation'),
        COUNT(*) FILTER (WHERE validation_type = 'update'),
        COUNT(*) FILTER (WHERE validation_type = 'expiration_report'),
        COUNT(*) FILTER (WHERE validation_type = 'conflict_report')
    INTO v_confirm_cnt, v_refute_cnt, v_update_cnt, v_expire_cnt, v_conflict_cnt
    FROM validation_records
    WHERE post_id = p_post_id AND is_deleted = FALSE;

    -- 获取作者信誉分（加权）
    SELECT COALESCE(reputation_score, 60.00) INTO v_author_rep
    FROM users u
    JOIN posts p ON p.user_id = u.id
    WHERE p.id = p_post_id;

    -- 可信度计算公式（详见 doc 24 判定树）
    -- 基础分 = 作者信誉 * 0.3 + 50 * 0.7
    -- 证实 +5/条，证伪 -8/条，更新 +2/条，过期报告 -10/条，冲突报告 -15/条
    v_credibility := v_author_rep * 0.3 + 50.0 * 0.7
                   + v_confirm_cnt * 5.0
                   - v_refute_cnt * 8.0
                   + v_update_cnt * 2.0
                   - v_expire_cnt * 10.0
                   - v_conflict_cnt * 15.0;

    -- 限制在 [0, 100]
    v_credibility := GREATEST(0.0, LEAST(100.0, v_credibility));

    -- 更新信息可信度字段
    UPDATE posts
    SET credibility_score = v_credibility,
        valid_count = v_confirm_cnt,
        invalid_count = v_refute_cnt,
        updated_at = CURRENT_TIMESTAMP
    WHERE id = p_post_id;

    RETURN v_credibility;
END;
$$ LANGUAGE plpgsql;
```

#### 4.3.2 SP02 sp_mark_expired_posts（标记过期信息）

```sql
CREATE OR REPLACE FUNCTION sp_mark_expired_posts()
RETURNS INTEGER AS $$
DECLARE
    v_affected INTEGER;
BEGIN
    -- 将已过期但状态仍为 published 的信息标记为 expired
    UPDATE posts
    SET status = 'expired',
        updated_at = CURRENT_TIMESTAMP
    WHERE is_deleted = FALSE
      AND status = 'published'
      AND expire_at IS NOT NULL
      AND expire_at < CURRENT_TIMESTAMP;

    GET DIAGNOSTICS v_affected = ROW_COUNT;

    -- 记录日志（写入 admin_operation_logs，actor_id=0 表示系统）
    INSERT INTO admin_operation_logs (admin_id, action, target_type, target_id, detail, created_at)
    SELECT 0, 'system_expire', 'post', id, '自动过期标记', CURRENT_TIMESTAMP
    FROM posts
    WHERE is_deleted = FALSE AND status = 'expired'
      AND updated_at = CURRENT_TIMESTAMP;

    RETURN v_affected;
END;
$$ LANGUAGE plpgsql;
```

#### 4.3.3 SP03 sp_detect_conflict（检测冲突信息）

```sql
CREATE OR REPLACE FUNCTION sp_detect_conflict(p_post_id BIGINT)
RETURNS INTEGER AS $$
DECLARE
    v_conflict_cnt INTEGER;
    v_location_id  BIGINT;
    v_post_start   TIMESTAMP WITH TIME ZONE;
    v_post_end     TIMESTAMP WITH TIME ZONE;
BEGIN
    -- 获取当前信息的地点与时间范围
    SELECT location_id, event_start_at, event_end_at
    INTO v_location_id, v_post_start, v_post_end
    FROM posts WHERE id = p_post_id;

    IF v_location_id IS NULL OR v_post_start IS NULL THEN
        RETURN 0;
    END IF;

    -- 查找同地点、时间重叠、状态为 published 的其他信息
    SELECT COUNT(*) INTO v_conflict_cnt
    FROM posts
    WHERE id <> p_post_id
      AND location_id = v_location_id
      AND status = 'published'
      AND is_deleted = FALSE
      AND event_start_at IS NOT NULL
      AND event_end_at IS NOT NULL
      AND event_start_at < v_post_end
      AND event_end_at > v_post_start;

    -- 若存在冲突，将当前信息标记为 conflict
    IF v_conflict_cnt > 0 THEN
        UPDATE posts
        SET status = 'conflict', updated_at = CURRENT_TIMESTAMP
        WHERE id = p_post_id AND status = 'published';
    END IF;

    RETURN v_conflict_cnt;
END;
$$ LANGUAGE plpgsql;
```

#### 4.3.4 SP04 sp_update_reputation（更新用户信誉分）

```sql
CREATE OR REPLACE FUNCTION sp_update_reputation(p_user_id BIGINT)
RETURNS NUMERIC(5,2) AS $$
DECLARE
    v_published_cnt   INTEGER;
    v_confirmed_cnt   INTEGER;
    v_refuted_cnt     INTEGER;
    v_reported_cnt    INTEGER;
    v_reputation      NUMERIC(5,2);
BEGIN
    -- 统计用户发布信息数
    SELECT COUNT(*) INTO v_published_cnt
    FROM posts WHERE user_id = p_user_id AND is_deleted = FALSE;

    -- 统计被证实的信息数
    SELECT COUNT(DISTINCT post_id) INTO v_confirmed_cnt
    FROM validation_records v
    JOIN posts p ON p.id = v.post_id
    WHERE p.user_id = p_user_id AND v.validation_type = 'confirmation' AND v.is_deleted = FALSE;

    -- 统计被证伪的信息数
    SELECT COUNT(DISTINCT post_id) INTO v_refuted_cnt
    FROM validation_records v
    JOIN posts p ON p.id = v.post_id
    WHERE p.user_id = p_user_id AND v.validation_type = 'refutation' AND v.is_deleted = FALSE;

    -- 统计被举报数
    SELECT COUNT(*) INTO v_reported_cnt
    FROM reports WHERE reporter_id = p_user_id OR target_user_id = p_user_id;

    -- 信誉分公式：基础分 60 + 证实 +3 + 发布 +0.5 - 证伪 -5 - 被举报 -2
    v_reputation := 60.0
                  + v_confirmed_cnt * 3.0
                  + v_published_cnt * 0.5
                  - v_refuted_cnt * 5.0
                  - v_reported_cnt * 2.0;

    v_reputation := GREATEST(0.0, LEAST(100.0, v_reputation));

    UPDATE users SET reputation_score = v_reputation, updated_at = CURRENT_TIMESTAMP
    WHERE id = p_user_id;

    RETURN v_reputation;
END;
$$ LANGUAGE plpgsql;
```

#### 4.3.6 SP08 sp_submit_validation（提交协同验证）

```sql
CREATE OR REPLACE FUNCTION sp_submit_validation(
    p_user_id BIGINT,
    p_post_id BIGINT,
    p_validation_type VARCHAR(30),
    p_content TEXT,
    p_evidence_urls TEXT[]
)
RETURNS BIGINT AS $$
DECLARE
    v_record_id BIGINT;
    v_post_author BIGINT;
BEGIN
    -- 校验：不能为自己的信息验证
    SELECT user_id INTO v_post_author FROM posts WHERE id = p_post_id;
    IF v_post_author = p_user_id THEN
        RAISE EXCEPTION '不能为自己的信息提交验证';
    END IF;

    -- 校验：信息状态必须为 published
    IF NOT EXISTS (SELECT 1 FROM posts WHERE id = p_post_id AND status = 'published') THEN
        RAISE EXCEPTION '信息状态不允许验证';
    END IF;

    -- 插入验证记录
    INSERT INTO validation_records (post_id, user_id, validation_type, content, evidence_urls, created_at)
    VALUES (p_post_id, p_user_id, p_validation_type, p_content, p_evidence_urls, CURRENT_TIMESTAMP)
    RETURNING id INTO v_record_id;

    -- 重算信息可信度
    PERFORM sp_recalc_credibility(p_post_id);

    -- 若为冲突报告，触发冲突检测
    IF p_validation_type = 'conflict_report' THEN
        PERFORM sp_detect_conflict(p_post_id);
    END IF;

    -- 更新作者信誉分
    PERFORM sp_update_reputation(v_post_author);

    RETURN v_record_id;
END;
$$ LANGUAGE plpgsql;
```

## 6. 物化视图设计

[doc 26](docs/26_数据库逻辑模型设计.md) 中的普通视图每次查询都会重新计算，对于聚合型视图（V06/V08/V09）会带来性能压力。openGauss 支持物化视图（Materialized View），可将聚合结果预计算并缓存。

### 6.1 物化视图清单

| 物化视图 | 名称 | 基础视图 | 刷新频率 | 用途 |
| -------- | ---- | -------- | -------- | ---- |
| MV01 | mv_post_validation_stats | V06 | 每小时 | 信息验证统计缓存 |
| MV02 | mv_user_reputation_ranking | V08 | 每日 | 用户信誉排行 |
| MV03 | mv_admin_dashboard | V09 | 每 10 分钟 | 管理员仪表盘 |
| MV04 | mv_location_post_count | V07 | 每日 | 地点信息数统计 |

### 6.2 物化视图定义

#### 6.2.1 MV01 mv_post_validation_stats

```sql
CREATE MATERIALIZED VIEW mv_post_validation_stats AS
SELECT
    p.id AS post_id,
    p.title,
    COUNT(*) FILTER (WHERE v.validation_type = 'confirmation') AS confirm_cnt,
    COUNT(*) FILTER (WHERE v.validation_type = 'refutation') AS refute_cnt,
    COUNT(*) FILTER (WHERE v.validation_type = 'update') AS update_cnt,
    COUNT(*) FILTER (WHERE v.validation_type = 'expiration_report') AS expire_cnt,
    COUNT(*) FILTER (WHERE v.validation_type = 'conflict_report') AS conflict_cnt,
    p.credibility_score
FROM posts p
LEFT JOIN validation_records v ON v.post_id = p.id AND v.is_deleted = FALSE
WHERE p.is_deleted = FALSE
GROUP BY p.id, p.title, p.credibility_score
WITH DATA;

-- 创建唯一索引（用于增量刷新）
CREATE UNIQUE INDEX idx_mv_post_validation_pk ON mv_post_validation_stats (post_id);

-- 刷新物化视图
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_post_validation_stats;
```

#### 6.2.2 MV03 mv_admin_dashboard

```sql
CREATE MATERIALIZED VIEW mv_admin_dashboard AS
SELECT
    (SELECT COUNT(*) FROM users WHERE is_deleted = FALSE) AS total_users,

    (SELECT COUNT(*) FROM reports WHERE status = 'pending' AND is_deleted = FALSE) AS pending_reports,
    (SELECT COUNT(*) FROM notifications WHERE is_deleted = FALSE) AS total_notifications,
    CURRENT_TIMESTAMP AS refreshed_at
WITH DATA;
```

### 10.2 查询性能估算

| 查询场景 | 优化前 | 优化后 | 优化手段 |
| -------- | ------ | ------ | -------- |

| 管理员仪表盘 | 1500ms（15+ 子查询） | 30ms | MV03 物化视图 |
| 标题模糊搜索 | 500ms（LIKE 全表） | 30ms | pg_trgm GIN 索引 |
| 过期信息扫描 | 100ms（全表） | 5ms | idx_post_expire_active 部分索引 |
| 未读消息计数 | 80ms（全表） | 3ms | idx_notification_unread 部分索引 |
| 评论树查询 | 120ms（递归 CTE） | 15ms | idx_comment_post_created 复合索引 |

### 10.3 性能优化建议

1. **连接池配置**：应用层使用 SQLAlchemy 连接池，pool_size=20, max_overflow=10
2. **预编译语句**：openGauss 支持 prepared statement，减少 SQL 解析开销
3. **批量插入**：批量数据使用 INSERT ... VALUES (...), (...), (...) 而非单条插入
4. **避免 SELECT ***：** 只查询必要字段，减少网络传输
5. **EXPLAIN ANALYZE**：上线前对所有关键查询执行执行计划分析
6. **统计信息更新**：每日 ANALYZE 关键表，确保优化器选择正确执行计划
