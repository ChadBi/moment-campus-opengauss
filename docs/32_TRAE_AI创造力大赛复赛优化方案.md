# 此刻校园 TRAE AI 创造力大赛复赛优化方案

> **历史方案（已废弃）**：本文中的“附近地点”、实时定位和学号+校园邮箱认证口径已被 2026-08-06 的《AI 地点摘要实施方案》替换。仅保留作为复赛材料演进记录，不得据此实现新功能。

## 摘要

“此刻校园”已从 14,000 个项目中晋级复赛，现有版本具备 React + FastAPI + openGauss 的完整全栈基础，已经实现校园信息流、地图发现、发布审核、搜索、互动、通知、个人中心与管理后台，并完成公网 HTTPS 部署。项目当前最有竞争力的资产是明确的校园真实场景、差异化的“校园生活地图”定位、较完整的产品链路、openGauss 工程深度以及可追溯的 TRAE 协作研发过程。

复赛阶段的目标不是继续平均扩充普通功能，而是围绕评审标准完成一次聚焦升级：**把当前工程型作品升级为具有真实 AI 使用价值、稳定体验、可信质量证据和完整交付材料的正式产品**。建议以“AI 驱动的校园时空信息发现与治理”为核心叙事，优先实现一条可验证、可降级、与现有业务高度结合的 AI 链路，同时修复代码、测试、文档和演示材料之间的事实偏差。

本方案建议采用“一个核心 AI 闭环、两条完整用户路径、三类质量证据、四组提交材料”的复赛策略，在 2026 年 8 月 9 日 23:59 前形成可直接体验和可被评审核验的正式作品。

## 1. 复赛要求与战略判断

### 1.1 官方硬性要求

根据官方复赛指南和本地《TRAE AI 创造力大赛·复赛详细说明》，软件类作品必须满足以下条件：

1. 延续初赛晋级作品，不另起炉灶。
2. 从 Demo 升级为核心功能齐全、必要页面完备、用户路径完整的正式产品。
3. 提供评审可直接访问的在线体验入口；有登录时必须提供有效测试账号。
4. 核心流程稳定，无严重 Bug，能够经受评审反复操作。
5. 技术架构清晰，AI 链路可验证。
6. 提供 1–5 分钟完整产品演示视频。
7. 提供不少于 3 个关键任务 Session ID 和不少于 3 张 TRAE 开发过程截图。
8. 先在社区复赛专区发布公开作品说明帖，再通过飞书问卷私密提交体验入口、测试账号、视频与其他作品材料。
9. 复赛新增核心能力必须使用 TRAE IDE 或 TRAE Work 完成，并保留可关联到实际成果的 Session ID、过程截图和提交记录，供评审核验。

复赛截止时间为 **2026 年 8 月 9 日 23:59（北京时间）**。评审以飞书问卷提交内容为准，社区帖主要承担公开展示与创作过程说明作用。提交截止后不得擅自补交、替换、撤回或修改，因此必须把提交演练和材料核验前置完成。

### 1.2 评分权重带来的优先级

“此刻校园”初赛按社会服务赛道准备。若复赛仍保持该赛道，五项评分均为 20%；若最终按通用赛道评审，则产品完成度和技术实现各占 30%。两种情形都指向相同结论：

| 战略重点 | 对应评分 | 本项目应采取的行动 |
|---|---|---|
| 正式产品而非功能样例 | 产品完成度 | 完整走通游客、用户、管理员三类路径，消除死链、假功能和错误文案 |
| AI 链路真实可验证 | 技术实现、创新性 | 实现真实模型调用、过程可观察、结果可解释、失败可降级的 AI 核心能力 |
| 高频校园问题有效解决 | 实用性 | 让用户更快找到“现在、附近、可信”的校园信息，而非只展示内容列表 |
| 可复制的校园公共信息服务 | 社会价值 | 证明方案可低成本迁移到不同高校，形成校园信息公共基础设施 |
| 差异化解决思路 | 创新性 | 强化“时空信息 + 生命周期 + 社区验证 + AI”的组合，而非泛化为校园论坛 |

### 1.3 总体战略

复赛版本的推荐定位为：

> **此刻校园是一张由校园成员和 AI 共同维护的校园生活地图，让分散、短暂、真假难辨的校园信息变得可发现、可验证、可更新。**

复赛开发应坚持以下原则：

- 不重做技术栈，不迁移数据库，不新增与竞赛目标无关的大型模块。
- 不把“使用 TRAE 开发”误写为产品内 AI；研发过程证明与产品 AI 链路分别展示。
- 不追求多个浅层 AI 按钮，优先完成一条高质量 AI 主链路。
- AI 不接管用户决策，所有推荐允许修改，所有失败均可回退到现有基础能力。
- 所有对外数字、功能描述和演示话术以复赛最终代码与实测结果为准。

### 2.2 必须正视的事实偏差

> 2026-07-31 现状更新：本节记录的差距已按批准计划收敛。协同验证固定为两类，自动过期 timer、动态分类、DataVec 混合检索/关键词降级和独立测试库均已落地；后续章节以该现行基线为准。

当前材料不能直接用于复赛提交，主要原因不是措辞问题，而是部分说明与代码实际行为不一致：

- 代码和现行材料统一只接受“证实、证伪”2 类协同验证，使用单数 `/validate` 写端点。
- 收藏功能已从主链路移除，但部分文档和测试仍在描述或调用收藏接口。
- 6 态状态机与独立 `moment-expire-posts.timer` 已接通；不宣称不存在的自动冲突检测。
- AI 搜索已接入 openGauss DataVec 512 维语义召回、35/25/20/20 混合排序和关键词降级。
- 历史自动化测试数量和覆盖率不能代表当前代码，部分测试仍依赖已删除功能。
- 作品帖仍有产品截图、TRAE 截图、Session ID、报名帖链接等占位内容。

这些偏差会直接损害评审对完成度、稳定性和真实性的判断。复赛第一原则是：**宁可准确展示已完成的 2 类验证，也不能演示不存在的 5 类能力；宁可给出新的真实测试结果，也不能沿用过期的“172 项全部通过”。**

### 2.3 复赛差距分级

| 优先级 | 差距 | 不解决的后果 |

| P0 | 产品内没有真实 AI 链路 | 难以满足“AI 链路可验证”，创新性和技术实现失去核心抓手 |
| P0 | 测试、文档、演示口径与代码不一致 | 评审操作时出现功能落差，真实性受质疑 |

| P0 | 线上环境尚未完成复赛期持续可用验证 | 体验入口失效会直接影响评审 |
| P1 | 缺少浏览器级核心链路自动化验证 | 难以证明真实用户路径稳定 |
| P1 | 搜索存在 N+1 查询和中文检索能力限制 | AI 搜索或普通搜索在数据量增长后可能不稳定 |

## 3. 核心产品升级方案

### 3.1 核心 AI 闭环：校园信息智能发现助手

建议把复赛最主要的新增能力定义为“校园信息智能发现助手”，解决用户无法用准确关键词描述需求的问题。例如：

- “晚上十点后还能打印彩色照片的地方”
- “离图书馆近、适合讨论又有插座的空间”
- “最近食堂有没有被多人确认过的新窗口”
- “这周末学校里有什么活动”

AI 链路不应另建一套与现有产品割裂的聊天机器人，而应直接增强现有搜索和地图：

```text
自然语言问题
  → AI 提取意图与结构化条件
  → openGauss 召回候选信息
  → 受控规则或 AI 对有限候选结果重排并生成理由
  → 权限、状态、有效期过滤
  → 信息流与地图同步展示
  → 用户打开详情、验证、评论或发布补充信息
```

推荐的结构化条件包括：关键词、分类、地点、时间范围、有效状态、距离倾向、可信度倾向。AI 返回内容必须经过 Pydantic Schema 校验，数据库查询继续通过 SQLAlchemy 参数化执行，禁止把模型文本直接拼接为 SQL。

智能搜索接口必须定义为统一结果模型，而不是把既有搜索页和地图页各自接入模型。推荐返回 `intent`、`items`、`candidate_ids`、`map_bounds` 与 `mode`，其中 `candidate_ids` 或受服务端保存的查询令牌用于让信息流和地图展示同一候选集，`map_bounds` 用于定位地图视图。只有这样，“搜索结果与地图同步”才是可实现、可测试、可演示的产品能力。

这一方案具有四个优势：

1. 与现有搜索、地图、分类、状态机直接复用，开发范围可控。
2. 直接使用 openGauss 7.0.0-RC3 原生 DataVec，不安装 pgvector，也不引入第二个数据库。
3. AI 服务不可用时可自动回退到关键词搜索和筛选，产品仍然可用。
4. 评审能够清楚看到“输入、AI 解析、数据库召回、结果解释、降级”的完整链路。

### 3.2 AI 辅助发布

在发布页增加与智能发现共用模型服务的“智能整理”能力：用户输入标题和正文后，AI 给出分类、标签、地点候选、有效期和内容摘要建议。所有结果仅作为可编辑建议，用户确认后才写入数据库。

AI 辅助发布的前置条件是先修复当前发布字段的端到端一致性。页面中填写或确认的地点、经纬度、标签、图片、有效期、草稿与分类，必须在请求载荷、数据库记录、审核结果和详情页中逐字段保持一致；未完成这项校验前，不得把“AI 推荐地点、标签、有效期”作为复赛功能展示。

该能力应保持克制：

- 不自动发布，不绕过审核。
- 不处理草稿以外的私人数据。
- 明确显示“AI 建议”，允许一键撤销或逐项修改。
- 模型不可用时继续使用当前手动表单，不阻断发布。
- 对模型请求设置超时、重试上限和输入长度限制。

智能发现解决“找不到”，智能发布解决“不会整理”，两者可共享统一的 AI 网关、Prompt 版本、Schema 校验、调用日志和降级机制。复赛范围上，智能搜索是 P0 必交能力；智能发布是在现有发布链路修复并通过回归后的 P1 加分能力，不得反向拖累主链路稳定性。

### 3.3 AI 可验证性设计

复赛要求“AI 链路可验证”，因此不能只展示一个结果。建议在不暴露敏感信息的前提下增加以下证据：

| 证据 | 用户界面 | 管理或技术界面 |
|---|---|---|
| 服务状态 | 显示智能模式或基础模式 | 健康检查显示 AI 服务可用性 |
| 意图解析 | 显示识别出的筛选条件，可由用户修改 | 保存脱敏后的结构化结果和耗时 |
| 结果依据 | 每条结果显示简短匹配理由 | 记录召回数、重排数、Prompt 版本 |
| 降级路径 | AI 失败时提示已切换基础搜索 | 记录失败类型，不记录 API Key |
| 隐私边界 | 提示仅处理当前输入与公开信息 | 不发送草稿历史、身份凭证和匿名作者信息 |

数据库可新增轻量的 `ai_invocation_logs` 或等价表，记录功能类型、成功状态、耗时、模型标识、Prompt 版本、降级原因和匿名化输入摘要。不得记录真实 API Key，不应完整保存可能包含敏感信息的原始 Prompt。

### 3.4 产品完整路径

复赛版本至少要稳定支持两条主路径：

**路径 A：校园信息发现与验证**

游客打开首页 → 使用自然语言智能搜索 → 查看信息流与地图结果 → 打开详情 → 登录 → 点赞/评论 → 证实或证伪 → 查看操作反馈与通知。

**路径 B：校园信息发布与治理**

普通用户登录 → 输入校园信息 → 用户确认 → 提交审核 → 管理员审核 → 用户收到通知 → 信息公开展示 → 社区持续验证。若 AI 辅助发布达到验收门槛，则在用户确认前提供可编辑建议。

管理员路径必须作为第二角色完整验证，而不是只展示后台静态页面。发布、审核、通知、公开展示应使用同一条新建数据完成闭环。

### 3.5 产品体验完善

在 AI 主链路之外，只处理直接影响评审体验的问题：

- 增加清晰的新用户空状态、错误状态、加载状态和重试入口。
- 统一“验证”“有效期”“状态”的中文文案，避免技术词汇直接暴露给普通用户。
- 对登录过期、接口超时、地图加载失败、AI 超时给出明确反馈。
- 确保桌面端和常见移动端宽度无文字溢出、遮挡和不可点击控件。
- 为测试账号准备稳定数据，避免评审进入后看到空页面或无可操作内容。
- 增加简洁的“体验指引”，但不在社区公开帖子中暴露测试账号和体验链接。

## 4. 技术实施方案

### 4.1 推荐架构

在现有 FastAPI 架构中新增独立 AI 模块，避免将模型调用散落在搜索和发布路由：

```text
前端 SearchPage / PublishPage
        ↓
FastAPI AI API
        ↓
AI Gateway
  ├─ Prompt 模板与版本
  ├─ Schema 校验
  ├─ 超时、重试、熔断
  ├─ 脱敏日志
  └─ 基础模式降级
        ↓
现有 Search / Post 查询能力
        ↓
openGauss
```

建议接口保持少而清晰：

- `POST /api/v1/ai/search-intent`：解析自然语言并返回结构化条件。
- `POST /api/v1/ai/search`：完成召回、重排和匹配理由生成。
- `POST /api/v1/ai/publish-assist`：返回分类、标签、地点、有效期与摘要建议。
- `GET /health/ai`：返回模型服务健康状态和降级状态，不返回密钥或内部配置。

若时间受限，可先实现统一的 `POST /api/v1/ai/search` 和 `POST /api/v1/ai/publish-assist`，避免为架构完整而过度拆分。

### 4.2 安全与可靠性

- API Key 仅通过服务端环境变量注入，前端、仓库、日志、截图和视频均不得出现明文。
- 为模型请求设置明确超时；超时或异常立即走基础搜索/手动发布。
- 使用固定 JSON 输出协议与严格 Schema，拒绝无法解析的模型结果。
- 模型输出只用于构造白名单筛选条件，不直接执行任意查询或代码。
- 对搜索与发布辅助接口增加频率限制和最大输入长度。
- 保留请求 ID，便于定位一次演示中的完整前后端链路。
- 对 AI 日志做数据最小化和脱敏，不记录 JWT、密码、匿名作者身份和完整个人信息。

### 4.3 搜索与性能优化

在接入 AI 前先消除现有搜索结果组装中的 N+1 查询，通过关系预加载或聚合查询一次获取分类、地点、作者、标签和图片。AI 只对数据库召回的有限候选集进行重排，建议候选规模固定并设置上限，避免每次把全库数据发送给模型。

性能验收不应继续只使用 30 条帖子。应生成更接近演示规模的数据，分别测量：

- 基础搜索数据库耗时。
- AI 意图解析耗时。
- 候选召回与重排总耗时。
- AI 超时后的降级耗时。
- 多次连续请求的成功率和 P95 响应时间。

报告中只引用实际测得的数据，不预设或虚构性能数字。

### 4.4 测试与质量证据

复赛质量验证分为三层：

1. **后端自动化测试**：在独立 `TEST_DATABASE_URL` 测试库中覆盖两类验证、AI Schema、DataVec 检索、超时降级、权限、状态过滤和日志脱敏。
2. **前端构建与关键组件验证**：至少保证 TypeScript 构建、ESLint 和 AI 搜索交互的关键状态正常；若交付辅助发布，则同步覆盖其关键状态。
3. **浏览器级 E2E**：覆盖“登录 → 发布 → 管理员审核 → 通知 → AI 搜索发现 → 验证”核心链路，并覆盖 AI 服务不可用时的降级路径；若交付辅助发布，再增加对应步骤。

最终应形成一份可复现的质量报告，包含环境、命令、通过数量、失败数量、覆盖范围和已知限制。不得继续引用未经本次回归验证的历史数字。

## 5. 评分维度专项方案

### 5.1 产品完成度

- 用两条真实数据链路证明产品从输入到结果完整闭环。
- 清理所有占位页面、无效入口、错误按钮和与代码不一致的功能说明。
- 验证游客、普通用户、管理员三种身份的权限与跳转。
- 准备固定、可重复操作的演示数据和测试账号。
- 确保线上体验在提交后至结果公示期间持续有效。

### 5.2 技术实现

- 展示 React、FastAPI、openGauss、Nginx、HTTPS 的清晰架构图。
- 重点解释 AI 网关、结构化输出校验、数据库召回、语义重排、降级和脱敏日志。
- 用自动化测试、E2E、性能数据和线上健康检查证明稳定性。
- openGauss 物理模型作为工程深度证据，但不抢占产品演示主线。

### 5.3 实用性

- 用“搜索群聊找不到、信息过期、真假难辨、地点信息分散”四个真实问题建立场景。
- 用任务完成时间、有效结果点击率或用户测试反馈证明智能搜索价值。
- 展示 AI 不只是生成文本，而是帮助用户完成“发现、发布、验证”的真实任务。
- **已落地「附近地点」**：`GET /locations/nearby` 按 Haversine 距离升序，定位到当前教学楼即可看“附近有什么”，并叠加**校内设施评分评价**（打印店、食堂、自习室打分），把分散的地点信息沉淀为「校园好去处」口碑库。

### 5.4 创新性

- 核心创新不是单独的聊天框，而是“自然语言意图 → 校园时空数据 → 生命周期过滤 → 社区验证”的组合。
- 强调 AI 与社区协同：AI 提高信息组织效率，社区成员提供事实验证，管理员处理治理边界。
- 展示可解释和可降级设计，避免把不可控生成结果直接当作事实。

### 5.5 社会价值

- 目标受众不仅是内容发布者，也包括刚入学、对校园不熟悉和信息获取渠道有限的学生。
- 产品降低校园公共信息获取门槛，减少信息差和重复询问。
- 通过学校、地点、分类和权限配置实现跨校复制；江南大学是唯一演示学校，不代表架构只能支持一所学校。
- **已落地「校园身份认证」**：学号 + 校园邮箱域名校验 + 一次性验证码，认证作者展示「已认证」徽标，让信息真实、同学可信任，从源头减少虚假/骚扰内容。
- **已落地「微信小程序」**：摆脱独立 App/Web 的安装门槛，微信里即扫即用，契合校园高频、碎片、移动的使用习惯，利于真实被使用起来。
- 后续可面向学校部门、社团、志愿服务组织建立可信官方信息源，但复赛不应临时扩张为复杂组织系统。

## 6. 冲刺执行计划

### 6.1 第一阶段：事实校准与质量基线（7 月 24 日–7 月 26 日）

目标是先让当前产品“说的和做的一致”。

- 协同验证最终固定为 2 类并统一全部现行材料，历史三类问题报告不纳入现行契约。
- 自动过期由独立 systemd timer/oneshot worker 执行；继续清理收藏和自动冲突等未实现能力的错误描述。
- 修复过期测试，先恢复可运行的完整测试基线，再执行后端完整回归；该项是进入 AI 开发的阻断门槛。
- 完成前端构建、Lint 和线上环境基础巡检。
- 固化复赛需求、技术方案和验收清单。

阶段门槛：现有非 AI 主链路稳定，材料口径与代码一致，所有已知 P0 Bug 有明确结论。

### 6.2 第二阶段：核心 AI 链路（7 月 27 日–7 月 31 日）

- 实现 AI Gateway、配置、Schema、超时和降级，并同步保留 TRAE Session ID、过程截图与成果关联证据。
- 优先完成自然语言意图解析、数据库候选召回与受控匹配理由，使用统一结果模型联动信息流和地图。
- 完成发布字段端到端一致性后，再实现 AI 辅助发布，保留用户确认和手动模式。
- 增加 AI 调用日志、健康检查和匹配理由。
- 为正常、异常、超时和恶意输出补充后端测试。

阶段门槛：智能搜索可在线使用；断开 AI 服务后基础功能仍可继续使用；API Key 不进入客户端和日志。辅助发布只有在发布字段一致性和相关回归测试通过后才进入候选版本。

### 6.3 第三阶段：体验、性能与端到端验证（8 月 1 日–8 月 4 日）

- 优化搜索 N+1 查询和 AI 候选集规模。
- 完成移动端、错误态、加载态和登录过期体验。
- 建立核心 E2E，连续重复走查用户与管理员闭环。
- 使用更接近演示规模的数据执行性能与稳定性测试。
- 部署复赛候选版本，配置可执行的监控、备份和回滚方案：健康探测频率、告警接收人、数据库备份位置、恢复步骤、候选版本标识与回滚版本标识均需记录。

阶段门槛：核心 E2E 可重复通过，线上无已知严重 Bug，质量报告中的数据均可复现。

### 6.4 第四阶段：材料制作与提交演练（8 月 5 日–8 月 7 日）

- 拍摄首页、地图、智能搜索、发布审核闭环、协同验证、管理后台等高清截图；辅助发布达到验收门槛后再纳入。
- 录制 1–5 分钟完整产品演示视频。
- 整理不少于 3 张 TRAE 开发过程截图和不少于 3 个关键 Session ID。
- 完成复赛产品说明书、社区作品帖和飞书问卷草稿。
- 完成一轮“不了解项目的评审视角”材料审读。

阶段门槛：所有占位符清零，社区公开内容不含体验链接、测试账号、源码包或敏感信息。

### 6.5 第五阶段：冻结与正式提交（8 月 8 日–8 月 9 日）

- 仅修复阻断性 Bug，不再增加新功能。
- 从全新浏览器和不同网络验证体验入口、视频链接与测试账号。
- 在 8 月 8 日前完成全量提交演练与材料核验；8 月 9 日仅提交已核验的最终版本，不假设问卷可修改。
- 先发布社区复赛作品帖，获得正式帖子链接。
- 再填写飞书问卷，提交体验入口、账号、视频、说明书和组队信息。
- 保存提交页面截图和全部材料的最终版本。

建议不要把提交动作拖到 8 月 9 日晚间。正式提交后不假设可以修改、替换或补交材料。

## 7. 演示与材料方案

### 7.1 1–5 分钟视频结构

推荐控制在约 4 分钟，并以真实操作为主：

| 时间 | 内容 | 证明目标 |
|---|---|---|
| 0:00–0:20 | 校园信息分散、过期、真假难辨的问题 | 场景真实、需求明确 |
| 0:20–0:45 | 首页与校园地图 | 产品定位与视觉辨识度 |
| 0:45–1:35 | 自然语言智能搜索，展示解析条件、结果理由和地图联动 | AI 主链路可见、可解释 |
| 1:35–2:20 | 发布审核闭环；若辅助发布已通过验收，则展示用户修改 AI 建议后提交 | 产品闭环，或进一步证明 AI 提升任务效率 |
| 2:20–3:00 | 管理员审核、普通用户收到通知、帖子公开 | 产品闭环与权限完整 |
| 3:00–3:30 | 社区证实/证伪、有效期与状态 | 可信协同机制 |
| 3:30–3:50 | AI 降级或健康状态、架构与测试证据 | 技术可靠性与可验证性 |
| 3:50–4:00 | 社会价值与跨校复制总结 | 实用性、创新性、社会价值 |

视频中不得展示 API Key、服务器密码、JWT、后台敏感日志或问卷私密信息。

### 7.2 社区作品帖

社区帖建议使用以下结构：

1. 个人或团队介绍。
2. 一句话产品定位和真实问题。
3. 从初赛 Demo 到复赛产品的升级对比。
4. 完整用户路径和核心功能，配真实截图或流程图。
5. 产品演示视频。
6. AI 链路、技术架构和降级机制。
7. TRAE 实践过程、开发截图和 Session ID。
8. 社会价值、可复制性和后续规划。

社区帖不得公开体验地址、测试账号、安装包、源码包或可复刻作品本体。当前 `Demo作品帖_此刻校园.md` 应改写为复赛版，并删除所有占位符和不真实描述。

### 7.3 飞书问卷私密材料

- 社区复赛作品帖链接。
- 初赛晋级作品链接。
- 线上体验入口和打开说明。
- 普通用户、管理员测试账号。
- 1–5 分钟产品演示视频链接或文件。
- 产品说明书同步存档。
- 组队信息与实际分工；若单人参赛则按问卷要求填写。
- 可选的架构图、测试报告、部署说明和源码说明。

### 7.4 TRAE 实践证明

Session ID 应覆盖不同类型的关键任务，而不是三个相似的小修复。建议选择：

- 产品与复赛方案设计。
- 核心 AI 链路实现与安全降级。
- 前后端完整闭环或复杂状态机实现。
- UI 设计系统与关键页面重构。
- openGauss 迁移、测试或生产部署问题排查。

每个 Session ID 在材料中附一句“任务目标、TRAE 贡献、最终产出”，并配对应代码、页面或部署结果截图，形成从对话到成果的证据链。

## 8. 验收指标

以下指标是复赛提交前的最低门槛，具体性能阈值应在基线测试后确定并记录，不在未测试前虚构数值：

| 类别 | 必须通过的验收项 |
|---|---|
| 产品 | 游客、用户、管理员路径均可从头走通；没有阻断性死链或严重 Bug |
| AI | 智能搜索真实调用模型；结果通过 Schema 校验；失败可降级；辅助发布仅在发布字段端到端一致后展示 |
| 安全 | API Key 不出现在前端、仓库、日志、截图和视频；权限接口完成校验 |
| 后端 | 使用 `backend/.venv` 执行完整测试，记录真实通过/失败数量 |
| 前端 | `npm run build` 和 `npm run lint` 通过，关键页面完成桌面与移动端检查 |
| E2E | 核心发布审核闭环、智能搜索闭环和 AI 降级闭环可重复通过 |
| 性能 | 基础搜索、AI 搜索、降级路径完成实测并形成可复现报告 |
| 部署 | HTTPS、健康检查、静态资源、API、地图、上传、登录均可公网访问 |
| 材料 | 视频、产品说明书、真实截图、3 个以上 Session ID、3 张以上过程截图齐全 |
| TRAE 过程 | 每项复赛新增核心能力均可关联到 TRAE Session ID、截图、代码或部署成果，队长能够说明核心方案 |
| 提交 | 社区帖与飞书问卷均完成，链接和账号在评审期持续有效 |

## 9. 风险与应对

| 风险 | 预警信号 | 应对措施 |
|---|---|---|
| AI 接口不稳定或延迟高 | 超时增加、演示中卡顿 | 设置超时与熔断，缓存安全结果，始终保留基础模式 |
| AI 功能做得过多导致主链路不稳 | 多个半成品入口、测试持续失败 | 冻结范围，优先交付智能搜索；辅助发布未达到验收门槛则不进入复赛版本 |
| 文档继续与代码漂移 | 演示脚本出现代码中不存在的按钮 | 建立单一事实清单，提交前逐条从实际界面核对 |
| 线上服务器故障 | 健康检查失败、证书或磁盘异常 | 每日巡检，准备数据库备份、前端静态备份和快速回滚步骤 |
| 测试账号被修改或数据污染 | 无法登录、演示内容消失 | 使用专用评审账号，限制危险操作，准备可重复初始化脚本 |
| 材料公开范围错误 | 社区帖出现体验链接或账号 | 建立公开/私密材料清单，发布前双人或双轮审查 |
| 截止前临时堆功能 | 8 月 8 日仍有数据库结构变更 | 8 月 7 日功能冻结，之后只修阻断问题 |
| Session ID 或截图证据不足 | 无法对应到实际成果 | 开发过程中同步登记，不在提交当天临时回忆和拼凑 |

## 10. 最终建议

“此刻校园”已经具备进入复赛深度打磨的工程基础，但当前版本的优势主要是完整全栈、地图场景、数据库设计和研发过程，尚未形成足够有说服力的产品 AI 价值。接下来的资源应集中在一个可被真实使用和验证的 AI 闭环上，并以事实一致性和稳定体验作为所有材料的底线。

最优复赛版本不是拥有最多功能的版本，而是评审在几分钟内能够明确理解并亲自验证：用户提出自然语言校园需求，AI 将需求转化为可信的时空条件，openGauss 返回真实校园信息，社区成员继续验证信息，管理员完成治理，系统在 AI 故障时仍然稳定可用。这个闭环同时覆盖产品完成度、技术实现、实用性、创新性与社会价值，是当前项目进入前 20 最值得投入的主线。
