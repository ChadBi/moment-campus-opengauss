## 1. 应用背景与具体应用场景

### 1.1 应用名称

**此刻校园（Moment Campus）**——基于 openGauss 的校园时空信息共享与可信协同平台

### 1.2 具体应用场景

以**江南大学蠡湖校区**为模拟核心（依据 [doc 23](docs/23_江南大学模拟核心决策说明.md)），面向校园成员（学生、教职工、管理员）提供校园生活信息的发布、浏览、验证、订阅与协同维护服务。

典型信息包括：
- 校园美食（哪个食堂窗口今天供应特色菜）
- 校园动物（哪里经常出现校园猫）
- 打印服务（哪家打印店营业、价格）
- 学习资源（图书馆座位情况、自习室开放状态）
- 校园活动（社团活动、讲座、演出）
- 校园设施（体育馆、游泳池开放情况）
- 失物招领（捡到/丢失物品信息）
- 校园兼职（兼职、实习信息）

### 1.3 调查方法

- **访谈法**：模拟对江南大学学生、社团负责人、食堂管理员、图书馆管理员、学生工作处老师的访谈
- **问卷法**：模拟收集 200 份学生问卷，了解信息获取痛点
- **观察法**：观察学生在微信群、QQ 群、朋友圈中发布和询问校园信息的行为
- **文献法**：参考已有校园信息平台（如北大未名、清华水木）的功能设计

## 2. 用户需求分析

### 2.1 用户痛点

| 编号 | 痛点 | 严重程度 | 出现场景 |
| ---- | ---- | -------- | -------- |
| P1 | 信息分散在群聊中，难以查找 | 高 | 找食堂今日菜单需翻多个群 |
| P2 | 信息时效性强但缺乏过期机制 | 高 | 看到旧信息以为图书馆还有座位 |
| P3 | 同一地点信息相互矛盾，难以判断 | 中 | 不同群友对同一窗口评价相反 |
| P4 | 信息发布后无人维护更新 | 高 | 维修公告维修完仍显示维修中 |
| P5 | 历史信息被覆盖后无法追溯 | 中 | 想查上周某活动是否举办 |
| P6 | 无法按地点快速发现附近信息 | 高 | 在图书馆附近想知道周边情况 |
| P7 | 难以判断信息是否可信 | 中 | 不确定某兼职信息是否真实 |
| P8 | 重要信息变化无通知 | 中 | 订阅的食堂窗口换菜不知道 |

## 5. 判定表与判定树

### 5.1 判定表 1：信息状态流转判定表

**判定目标**：根据当前状态与触发事件，判定信息的新状态

**条件桩**：

| 条件 | 取值 |
| ---- | ---- |
| C1 当前状态 | S1=draft, S2=pending_review, S3=published, S4=expired, S5=conflict, S6=archived |
| C2 触发事件 | E1=提交审核, E2=审核通过, E3=审核拒绝, E4=到期, E5=检测到冲突, E6=冲突解决, E7=管理员归档, E8=用户续期 |

**判定表**（行为新状态，—表示不允许该转换）：

| 当前状态 \ 事件 | E1 提交审核 | E2 审核通过 | E3 审核拒绝 | E4 到期 | E5 冲突 | E6 冲突解决 | E7 归档 | E8 续期 |
| -------------- | ----------- | ----------- | ----------- | ------- | ------- | ----------- | ------- | ------- |
| S1 draft | S2 | — | — | — | — | — | S6 | — |
| S2 pending_review | — | S3 | S1 | — | — | — | S6 | — |
| S3 published | — | — | — | S4 | S5 | — | S6 | — |
| S4 expired | — | — | — | — | — | — | S6 | S3 |
| S5 conflict | — | — | — | — | — | S3 | S6 | — |
| S6 archived | — | — | — | — | — | — | — | — |

**说明**：
- 草稿（S1）只能由用户提交审核转为待审核（S2）
- 待审核（S2）由管理员审核，通过则发布（S3），拒绝则退回草稿（S1）
- 已发布（S3）到期自动过期（S4），检测到冲突转为冲突态（S5），管理员可归档（S6）
- 已过期（S4）用户可续期回到发布（S3），管理员可归档（S6）
- 冲突（S5）由管理员解决后回到发布（S3），或直接归档（S6）
- 已归档（S6）为终态，不可再转换

### 5.3 判定表 2：举报处理判定表

**判定目标**：根据举报类型与证据情况，判定举报处理结果

**条件桩**：

| 条件 | 取值 |
| ---- | ---- |

**判定表**（行为处理动作）：

| T2 违法违规 | 删除+封禁7天 | 删除+封禁30天 | 删除+永久封禁 | 删除+封禁7天 | 删除+封禁30天 | 删除+永久封禁 | 转人工 |

### 5.4 判定树 2：可信度计算判定树

**判定目标**：根据验证记录与时间衰减，判定信息可信度等级

```
                  ┌──────────────────────┐
                  │  可信度计算 (Score)    │
                  └──────────┬───────────┘
                             │
                    计算综合得分
                  Score = (N_c - N_r) × α × R
                  其中 α = 时间衰减系数
                       R = 验证者信誉均值
                             │
              ┌──────────────┼──────────────┐
              │              │              │
        Score ≥ 70     30 ≤ Score < 70   Score < 30
              │              │              │
              ▼              ▼              ▼
        ┌──────────┐  ┌──────────┐   ┌──────────┐
        │ 高可信    │  │ 中可信    │   │ 低可信    │
        │ 可推荐   │  │ 正常显示  │   │ 标记警告  │
        │ 置顶候选 │  │          │   │ 加入冲突 │
        │          │  │          │   │ 检测队列  │
        └──────────┘  └──────────┘   └──────────┘
              │              │              │
              │              │              │
              ▼              ▼              ▼
        信誉加分         信誉不变       信誉减分
        +2 / 验证        ±0            -2 / 反驳
```

## 7. 需求分析结论

### 7.1 核心需求确认

| 需求类别 | 需求数 | 优先级分布 |
| -------- | ------ | ---------- |
| 普通用户需求 | 13 | P0×9, P1×4 |
| 管理员需求 | 8 | P0×5, P1×2, P2×1 |
| 系统需求 | 5 | P1×5 |
| **合计** | **26** | **P0×14, P1×11, P2×1** |

### 7.2 关键业务规则

1. **信息状态流转规则**：6 态状态机，受 [5.1 节判定表](#51-判定表-1信息状态流转判定表) 约束
2. **协同验证规则**：5 类验证，每用户对每条信息每类验证只能提交一次
3. **可信度计算规则**：综合验证数、时间衰减、用户信誉，受 [5.4 节判定树](#54-判定树-2可信度计算判定树) 约束
4. **权限控制规则**：基于角色（user/admin/super_admin）+ 信息状态，受 [5.5 节判定表](#55-判定表-3用户操作权限判定表) 约束
5. **举报处理规则**：5 类举报 × 3 级证据 × 3 级次数，受 [5.3 节判定表](#53-判定表-2举报处理判定表) 约束
