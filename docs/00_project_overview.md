# 项目总览

> 此刻校园 · Moment Campus
>
> **现行边界补充（2026-08-07）**：本文保留为项目基线参考。涉及实时定位、位置权限、距离或“附近”的早期描述均已废弃；当前实现以《此刻校园：AI 地点摘要实施方案》和《小程序契约矩阵与重构执行记录》为准，地图只组织学校静态地点，不采集用户当前位置。

## 1. 项目背景

### 1.1 校园信息现状

大学校园中存在大量真实、有用但容易消失的信息：

- 哪里有好吃的食堂窗口
- 哪家打印店价格更低、服务更好
- 哪里经常出现校园小猫
- 哪些地方适合拍照打卡
- 哪些教室适合自习
- 哪些店铺支持校园配送
- 最近的社团活动信息
- 哪里可以维修电脑或自行车
- 校园中的失物招领信息
- 校园内的便民服务

### 1.2 核心问题

这些信息目前主要分散在：

- 微信群、QQ群
- 朋友圈、空间
- 表白墙、校园论坛
- 口口相传

**存在的问题：**

1. **信息易逝**：发布得快，消失得也快，无法长期沉淀
2. **重复询问**：用户常常需要反复询问相同的问题
3. **难以验证**：很难判断以前的信息是否仍然有效
4. **缺乏组织**：信息分散，难以系统化查找
5. **无法沉淀**：有价值的信息随时间流失

### 1.3 产品机会

校园需要一个专门的信息平台，能够：

- 将分散的校园信息集中组织
- 让信息可搜索、可浏览、可验证
- 通过社区共同维护确保信息有效性
- 让有价值的信息长期沉淀

## 2. 产品定位

### 2.1 一句话定位

**"此刻校园"是一个基于校园地图的信息发现与共享平台，由校园成员共同建设和维护。**

### 2.2 产品形态

产品不是传统校园论坛，也不是普通信息列表社区，而是一张由校园成员共同维护的"校园生活地图"。**地图是用户进入系统后最主要、最醒目的操作区域**，所有信息围绕地图组织和发现。

**核心特征：**

- **地图优先**：地图是核心交互区域，占据主要视觉空间，用户进入首页即看到校园地图和各类信息标记点
- **地点为中心**：信息围绕地点组织，形成地点知识库
- **社区验证**：通过社区共同维护确保信息有效性
- **轻量发布**：简单几步即可完成信息发布
- **长期沉淀**：有价值的信息持续存在并不断更新

### 2.3 差异化优势（为什么学生会持续用）

针对导师反馈中"没有解决用户为什么用的动力"这一核心关切，本版在一般校园论坛之上建立了三个独特壁垒：

1. **真实可信（认证 + 来源）**：普通校园论坛匿名混杂、信息难辨真假。此刻校园使用登录教育邮箱完成校园认证，认证用户带「已认证」徽标；地点稳定资料由认证用户提议、管理员审核，动态摘要逐条保留来源。看得见谁在说、说的是哪里、依据是什么——信任是留存的起点。
2. **即时可用（地点 + 摘要 + 评分）**：地点详情先展示已审核稳定资料，再展示经过管理员审核的近期动态摘要，并提供原始帖子、评价和评分，帮助用户快速判断信息是否仍然适用。
3. **随手可得（小程序）**：无需下载 App，微信里即扫即用。校园场景是高频、碎片、移动的，小程序形态让"随手查看地点、随手分享"成为可能，大幅降低使用门槛。

这三点共同回答"用户为什么用、为什么持续用"：**真实的人、可追溯的地点、随手可得**。

### 2.4 产品边界

**当前版本包含：**
- 校园信息发布与浏览
- 地图与信息流结合
- 当前学校动态分类筛选与搜索，分类数量和名称由租户配置决定
- 协同治理（2 类互斥验证：证实/证伪，可切换或取消）
- 评论、点赞
- 6 态状态机（draft/pending/published/expired/conflict/archived）与管理员审核
- 移动端适配（响应式设计 + Service Worker）
- **微信小程序**：与 Web 同后端的小程序客户端，覆盖地点详情、地图、发布、认证等核心链路
- **多学校切换（多租户架构）**：支持江南大学、复旦大学、浙江大学三校
- **校园身份认证**：使用登录教育邮箱发送一次性 6 位数字验证码，认证用户展示「已认证」徽标，提升信息可信度
- **地点知识层**：地点稳定资料提议与管理员审核、AI“此刻摘要”、来源追溯、冲突提示和评分评价
- **AI 能力**：AI 地点摘要（管理员审核后发布）、AI 辅助搜索、DataVec 混合检索、AI 辅助发布建议（支持标题/正文优化）、AI 敏感信息检测
- **举报与后台管理**：管理员审核、报告处理、用户管理
- **内容订阅与推荐**：基于分类/地点/专题的订阅与推荐
- **平台管理**：套餐/用量/学校导入/激活漏斗（super_admin）

**当前版本不包含：**

- 关注系统与私信
- 收藏及“我的收藏”列表
- 复杂多级组织权限
- WebSocket 实时通知（使用轮询替代）

## 3. 核心价值

### 3.1 对用户

**信息发现**

- 快速找到需要的校园信息
- 通过静态校园地图和地点详情发现有用信息
- 通过分类浏览探索校园生活

**信息验证**

- 查看信息是否仍然有效
- 看到多少人确认有效
- 对信息进行证实或证伪，并查看两类验证统计

**信息分享**

- 轻松发布校园信息
- 帮助其他校园成员
- 形成个人校园贡献记录

### 3.2 对校园

**信息沉淀**

- 形成可持续更新的校园公共信息库
- 有价值的信息长期存在
- 减少重复询问

**社区建设**

- 促进校园成员之间的信息共享
- 形成互助的校园社区氛围
- 增强校园归属感

**知识传承**

- 新生可以快速了解校园
- 老生可以分享校园经验
- 形成校园生活知识体系

## 4. 目标用户

### 4.1 主要用户群体

**1. 新生**

- 刚进入学校，对校园不熟悉
- 需要快速了解校园生活
- 需要找到各种服务设施

**2. 在校学生**

- 希望探索校园生活
- 愿意分享校园经验
- 需要查找特定信息

**3. 内容发布者**

- 愿意分享校园信息
- 希望帮助其他同学
- 形成个人贡献记录

**4. 校园社团和学生组织**

- 发布活动信息
- 宣传社团活动
- 招募新成员

**5. 便民服务提供者**

- 校内打印店、维修店
- 配送服务
- 其他校园服务

**6. 交换生、访客和毕业校友**

- 临时了解校园信息
- 回忆校园生活
- 保持与校园的联系

**7. 平台运营人员**

- 内容审核
- 社区管理
- 运营维护

### 4.2 用户特征

- 年龄：18-25 岁为主
- 设备：移动端为主，桌面端为辅
- 习惯：习惯使用微信、小红书等社交平台
- 需求：快速、准确、有用的校园信息

### 5.1 第一版目标

**用于：**

- TRAE AI 创造力大赛
- 项目演示
- 产品路演
- 用户测试
- 后续真实开发

**核心目标：**

1. 完成核心用户闭环
2. 验证产品概念
3. 收集用户反馈
4. 为后续开发奠定基础

### 5.2 用户闭环

产品需要形成以下完整用户闭环：

```
发现校园信息
    ↓
查看信息详情
    ↓
搜索特定信息
    ↓
发布校园信息
    ↓
点赞和评论
    ↓
确认信息是否仍然有效
    ↓
纠正或补充信息
    ↓
形成可持续更新的校园公共信息库
```

### 5.3 长期愿景

- 覆盖更多学校
- 持续完善已落地的 AI 搜索、DataVec 混合检索和智能推荐
- 形成校园知识图谱
- 成为校园生活基础设施

## 6. 产品设计原则

### 6.1 地图优先

**地图是核心交互区域**，占据主要视觉空间。用户进入产品后：

- 首先看到校园地图和各类信息标记点
- 通过地图发现校园中的各类信息点位
- 点击标记查看详情、点赞、评论
- 支持地图缩放、拖动、定位、分类筛选
- 可切换到列表模式作为补充视图

**主页面重点突出三个动作：**
1. 查看校园地图
2. 搜索或筛选信息
3. 发布新的校园点位

### 6.2 信息优先

用户查看信息详情时，应快速了解：

- 这是什么信息
- 信息位于哪里
- 距离有多远
- 信息什么时候发布
- 信息是否仍然有效
- 有多少人确认有效
- 是否值得前往
- 是否存在补充或争议信息

### 6.3 地图与列表结合

产品采用"地图模式为主，列表模式为辅"的设计：

- **地图模式**：负责发现学校地点和相关动态，是空间组织视图
- **列表模式**：负责展示校园中正在发生的事情，是补充视图
- **视图切换**：用户可随时在两种模式间切换

### 6.4 轻量发布

发布流程应尽可能简单：

```
选择分类
    ↓
选择地点
    ↓
填写标题和描述
    ↓
上传图片
    ↓
选择失物类型（可选）
    ↓
设置有效期
    ↓
预览并发布
```

### 6.5 社区共同验证

校园信息的可信度通过社区共同维护。

2 类协同验证：

- **证实（confirmation）**：确认信息仍然有效
- **证伪（refutation）**：指出信息不准确或已经失效

每名用户对每条帖子仅保留一条验证记录，可在两类之间切换，再次点击同类即取消。单数写端点为 `POST /api/v1/posts/{post_id}/validate`，登录态统计端点为 `GET /api/v1/posts/{post_id}/validation-stats`。历史版本规划的更新建议、过期报告、冲突报告三类治理值已经废弃，不属于当前接口或完成范围。管理员审核与独立 systemd timer 自动过期任务共同维护信息生命周期。

### 6.6 动态分类与智能检索

- 分类由当前学校 API 动态加载，前端不使用固定分类 ID 或中文名称映射
- 分类视觉由 `category.code` 稳定计算，切换学校时清理旧校分类、筛选和地图标记
- AI 搜索使用 openGauss DataVec 512 维语义召回，并按语义 35%、新鲜度 25%、验证数 20%、关键词 20% 混合排序
- Embedding 或向量查询不可用时自动降级为关键词检索
- 后端测试只读取独立 `TEST_DATABASE_URL`，并拒绝数据库名不含 `_test` 或与开发库相同的连接串

### 6.7 隐私保护

产品不得默认收集用户的精确行动轨迹。

位置能力应遵循：

- 用户主动授权
- 用户主动选择地点
- 支持模糊地点
- 不读取私人聊天记录
- 不读取通讯录
- 不分析私人活动轨迹
- 联系方式默认非必填
- 发布前进行敏感信息提醒

### 6.7 内容沉淀

平台不应只追求短期信息流热度。

产品需要通过地点页、专题、搜索和有效性验证，使有价值的信息持续存在。

## 7. 成功指标

### 7.1 第一版成功指标

**产品指标：**

- 完成所有 P0 功能
- 核心用户闭环可走通
- 演示环境可正常访问

**用户指标：**

- 可演示完整用户流程
- 用户测试反馈积极
- 收集到有效用户反馈

**技术指标：**

- 系统稳定运行
- 无明显安全漏洞
- 性能满足基本要求

### 7.2 长期成功指标

**用户指标：**

- 日活跃用户数（DAU）
- 月活跃用户数（MAU）
- 用户留存率
- 信息发布量

**内容指标：**

- 信息总量
- 有效信息比例
- 社区验证活跃度
- 信息更新频率

**社区指标：**

- 用户参与度
- 内容质量评分
- 举报处理效率
- 用户满意度
