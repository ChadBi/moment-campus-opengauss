## 1. 项目定位

### 1.1 项目名称

- 中文名称：**此刻校园**
- 英文名称：**Moment Campus**
- 课程设计暂定题目：**基于 openGauss 的"此刻校园"时空信息图谱与可信协同平台设计与实现**

依据：[`docs/"此刻校园"项目初步方案说明`](docs/%22此刻校园%22项目初步方案说明) 第 1.1 节

### 1.2 当前仓库实际定位

当前仓库代码实现的是**原始方案（Base 版本）**：一个"校园地图信息共享平台"。

依据：
- `README.md` 第 7-11 行明确写明："此刻校园"是一个面向大学校园的信息共享与沉淀平台……产品不是传统校园论坛，也不是普通社交平台，而是一张由校园成员共同维护的"校园生活地图"。
- `docs/"此刻校园"项目初步方案说明` 第 3.1 节"原始定位"明确说明原始方案就是"校园信息共享平台"。
- 后端模型层（`backend/app/models/`）目前只实现了原始方案中的实体（Post、Comment、Like、Favorite、ValidationRecord 等），**没有**实现"调整后方案"中要求的可信度、信息版本、状态流转、冲突检测、地点订阅等核心升级实体。

### 1.3 目标定位（待改造）

根据 `docs/"此刻校园"项目初步方案说明` 第 6 节，目标项目要改造为"**校园时空信息图谱与可信协同平台**"，核心目标是"记录校园信息从产生、验证、变化、冲突到失效的完整过程"。详细差异见 [19_Base项目与目标项目差异说明.md](docs/19_Base项目与目标项目差异说明.md)。

## 4. 前后端架构

### 4.1 后端分层架构

```
HTTP 请求
  ↓
FastAPI 中间件层（app/middleware.py: RequestLoggingMiddleware + CORS）
  ↓
路由层（app/api/*.py）—— 直接编写 SQLAlchemy 查询，无独立 Service 层
  ↓
依赖注入层（app/dependencies.py: get_current_user / get_current_admin）
  ↓
数据模型层（app/models/*.py: SQLAlchemy 2.0 Mapped 风格）
  ↓
SQLAlchemy AsyncSession（app/database.py: async_session_maker）
  ↓
aiosqlite → SQLite 文件（dev.db）
```

**关键特征**：
- 无独立 Service 层（`app/services/` 与 `app/utils/` 为空目录）
- 路由层直接调用 `db.execute(select(...))`，业务逻辑与数据访问混在路由函数中
- 使用 SQLAlchemy 2.0 新版 `Mapped` + `mapped_column` 语法
- 全异步（`AsyncSession`、`create_async_engine`）

### 4.2 前端架构

```
浏览器
  ↓
main.tsx（QueryClientProvider 包裹 AppRoutes）
  ↓
routes.tsx（BrowserRouter + 懒加载 + ProtectedRoute 守卫）
  ↓
MainLayout（Header + Sidebar + MobileNav 响应式布局）
  ↓
pages/*.tsx（页面组件，useEffect + useState 管理数据获取）
  ↓
services/*.ts（axios 实例 + 按模块拆分的 API 方法）
  ↓
store/*.ts（zustand：useAuthStore 持久化 token / useCampusStore / useUIStore）
  ↓
axios → http://localhost:8000/api/v1
```

**关键特征**：
- `main.tsx` 是真正入口（`App.tsx` 是 Vite 默认模板，**未使用**，属于历史遗留）
- 使用 `@tanstack/react-query` 作为 QueryClient，但页面中实际更多使用 `useEffect + useState` 直接调用 `services/*.ts`，未充分利用 Query 能力
- `useAuthStore` 使用 `zustand/persist` 持久化到 localStorage（key: `auth-storage`）
- axios 拦截器自动注入 Bearer Token，401 时尝试 refresh

## 5. 当前数据库方案

### 5.1 连接方式

- 引擎：`create_async_engine(settings.DATABASE_URL, echo=settings.DEBUG)`，见 [backend/app/database.py](backend/app/database.py) 第 5-8 行
- 会话工厂：`async_sessionmaker(engine, class_=AsyncSession, expire_on_commit=False)`
- 依赖注入：`get_db()` 通过 `async with async_session_maker() as session` 提供会话
- 默认 URL：`sqlite+aiosqlite:///./dev.db`（见 [backend/app/config.py](backend/app/config.py) 第 12 行）

### 5.2 数据库初始化方式（重要）

仓库存在**两种并存的初始化路径**，且互不一致：

1. **Alembic 路径（README 推荐，但实际无效）**
   - README 第 100 行声称使用 `alembic upgrade head` 初始化
   - 但 [backend/alembic/versions/82978de89068_initial_migration_create_all_21_tables.py](backend/alembic/versions/82978de89068_initial_migration_create_all_21_tables.py) 的 `upgrade()` 和 `downgrade()` 函数体都只有 `pass`
   - 即 Alembic 迁移实际上**不创建任何表**

2. **Base.metadata.create_all 路径（实际使用）**
   - [backend/scripts/seed_data.py](backend/scripts/seed_data.py) 第 32-35 行的 `init_db()` 调用 `await conn.run_sync(Base.metadata.create_all)`
   - [backend/tests/conftest.py](backend/tests/conftest.py) 第 36-37 行测试夹具同样使用 `Base.metadata.create_all`
   - 即真正的建表是通过 `seed_data.py` 在填充演示数据前完成的
   - **后端 `main.py` 启动时不会自动建表**

### 5.4 字段类型使用情况

通过阅读 [backend/app/models/](backend/app/models/) 下的所有模型，字段类型汇总：

| SQLAlchemy 类型 | 使用场景 | openGauss 兼容性 |
| --------------- | -------- | ---------------- |
| `Integer` | 所有主键 `id`、计数类字段（view_count 等） | 兼容 |
| `BigInteger` | **所有外键字段**（user_id、school_id、post_id 等） | 兼容，**但与主键类型不匹配，详见下方风险** |
| `String(n)` | 标题、邮箱、昵称、状态枚举等 | 兼容（映射为 `VARCHAR(n)`） |
| `Text` | 长文本（Post.content、Comment.content 等） | 兼容 |
| `Boolean` | is_deleted、is_active、is_top 等 | 兼容 |
| `DateTime` | created_at、updated_at、expire_at 等 | 兼容 |
| `Numeric(10, 7)` | Location.latitude / longitude | 兼容 |
| `Float`（隐式） | School.center_lat / center_lng（未显式指定类型） | 兼容 |

**未使用**的类型：`JSON` / `JSONB`、`ARRAY`、`ENUM`、`UUID`、`Interval`。这是一个有利因素——没有需要专门适配的高级类型。

### 5.5 时间字段默认值

- 全部使用 **Python 端**默认值：`default=datetime.now`、`onupdate=datetime.now`
- **未使用** SQL 端函数（如 `NOW()`、`CURRENT_TIMESTAMP`）
- 这一点对 openGauss 适配有利，无服务端函数兼容性问题

## 10. 当前项目存在的主要问题

### 10.1 数据库层（与 openGauss 适配直接相关）

1. **主键 / 外键类型不一致**：所有主键为 `Integer`，所有外键为 `BigInteger`。在 SQLite 中可以正常运行（SQLite 忽略整型尺寸），但在 openGauss/PostgreSQL 中 `INT4` 列无法被 `INT8` 外键引用，**会导致外键约束创建失败**。依据：[`AIwork/SQLite主键类型修改.md`](AIwork/SQLite主键类型修改.md)
2. **Alembic 初始迁移为空**：`82978de89068_initial_migration_create_all_21_tables.py` 的 `upgrade()` 与 `downgrade()` 均为 `pass`，实际不建表。建表依赖 `seed_data.py` 中的 `Base.metadata.create_all`，导致迁移流程与 README 描述不符
3. **缺少 PostgreSQL/openGauss 驱动**：`requirements.txt` 仅含 `aiosqlite`，无 `asyncpg`/`psycopg2`
4. **README 与实际不符**：README 宣称"PostgreSQL（生产）"，但代码与依赖均未落地

### 10.2 代码层

1. **无独立 Service 层**：业务逻辑与数据访问混在 `api/*.py` 路由函数中，例如 [backend/app/api/search.py](backend/api/search.py) 在路由函数内进行 N+1 查询（每条 post 单独查询 category/location/user/tags/cover_image）
2. **前端 `App.tsx` 是 Vite 默认模板**：未被使用（实际入口是 `main.tsx` → `routes.tsx`），属于历史遗留
3. **前端未充分利用 React Query**：`main.tsx` 配置了 QueryClient，但页面中大量使用 `useEffect + useState` 直接调用 API，未利用 Query 的缓存与自动刷新能力
4. **`search.py` 中 `post_ids = [row[0] for row in post_tag_result.fetchall()]` 后又 `Post.id.in_(post_ids)`**：先全量取出再 `IN`，效率低且可能爆内存

### 10.3 文档层

1. **README 引用的 18 份 docs 文档实际不存在**：第 30-51 行的文档目录表与仓库实际状态严重不符
2. **`DEVELOPMENT_TASKS.md` 部分过时**：例如阶段二/三/四的勾选状态与代码实际进度不一致
3. **`.trae/specs/implement-full-project/spec.md` 仍写"SQLite 开发数据库、PostgreSQL 生产数据库"**：未反映 openGauss 改造要求
4. **`docs/` 下文件名包含中文引号**：`"此刻校园"项目初步方案说明` 文件名含全角引号，shell 操作时需转义，建议重命名（本次任务不修改）

### 10.4 与目标项目的差距

当前 Base 项目实现的是"地图版校园论坛"，与目标项目"时空信息图谱与可信协同平台"存在本质差距：缺少信息生命周期、协同验证、可信度、版本管理、冲突检测、时间轴等核心能力。详见 [19_Base项目与目标项目差异说明.md](docs/19_Base项目与目标项目差异说明.md)。
