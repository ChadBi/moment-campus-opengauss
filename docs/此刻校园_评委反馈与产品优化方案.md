# 此刻校园：AI 地点摘要实施方案

> 文档属性：内部实施方案（2026-08）
>
> 本文只描述可执行的产品边界、数据契约、开发顺序和验收方式。文中“目标界面示意”均为待实现或持续迭代的界面，不代表当前版本已经上线。

## 1. 评委反馈与已核实现状

### 1.1 评委反馈归纳

评委关注点集中在三件事：地点信息是否比帖子流更容易理解，动态内容是否有可靠依据，产品是否能在校园场景形成可持续的资料沉淀。原方案对定位、差异化和首页叙述重复较多，没有把“事实资料”和“近期动态”拆开，也没有清楚标注已经实现与待开发能力。

### 1.2 当前产品现状

| 模块 | 已核实状态 | 口径 |
| --- | --- | --- |
| 首页 | 已实现 | 目前是“推荐 + 帖子流”，不承载地点摘要生成。 |
| 地图 | 已实现 | 统一展示地点标记，地点面板可查看相关帖子；地图负责空间组织，不读取用户当前位置。 |
| 地点页 | 已实现 | 可查看地点基础信息、评分和评价；当前版本尚无 AI 摘要。 |
| 校园认证 | 已实现 | 使用用户登录时的教育邮箱发送验证码/认证链接，不再填写学号或第二邮箱。 |
| 地点稳定资料 | 本轮开发 | 认证用户提议，管理员审核后写入事实表。 |
| AI 地点摘要 | 待开发 | 只整理近期动态，生成结果必须进入管理员审核队列。 |

### 1.3 现状与方案的边界

当前地图坐标、地点标记和帖子地点关联继续保留。产品不采集用户实时位置，不提供按距离筛选、距离展示或最近排序。历史任务、提交记录和测试报告中的旧称谓不改写，但旧方案应标记为废弃，避免继续作为产品口径引用。

## 2. 最终产品边界

### 2.1 核心链路

```text
地点 → 稳定资料 → 近期动态 → AI 整理 → 来源追溯 → 用户补充
```

- **地点**是内容的组织单元，不是个人位置服务。
- **稳定资料**描述营业时间、服务、价格、联系方式、进入方式和预约方式等低频事实；资料由认证用户提议，管理员整份批准或驳回。
- **近期动态**来自当前学校、当前地点的已发布内容和评价，按时间窗口与状态过滤。
- **AI 整理**只做归纳，不替代稳定资料，也不能自行补充事实。
- **来源追溯**必须能回到原帖、原评价或已审核资料；管理员审核摘要时同时查看每条结论与原始来源。
- **用户补充**只进入提议队列，不能直接覆盖公开资料。

### 2.2 产品决策

1. 彻底移除实时定位、位置授权说明、距离字段、距离计算、按距离筛选和 `nearest` 排序。保留学校静态地图、地点坐标和帖子地点关联。
2. 地点详情优先于首页改版。首页和地图后续只消费已审核摘要，不在访问时现场生成。
3. 地点稳定资料与 AI 摘要严格分层。AI 不能改写稳定资料。
4. 所有摘要版本必须管理员审核后发布；驳回、超时或 AI 失败时继续展示最近一次已批准版本。
5. 证据不足时不生成具体结论，使用“暂无足够近期信息”空状态。
6. 继续使用昵称和校园认证标识，不公开真实姓名、学号或教育邮箱。

### 2.3 已实现 / 本轮开发 / 后续设想

- **已经实现**：学校租户隔离、地点标记与坐标、地点相关帖子、评分评价、教育邮箱认证、管理员地点核验。
- **本轮开发**：稳定资料提议与审核、AI 摘要来源快照、待审版本、管理员审核、地点详情接入、异步 dirty 刷新、旧“附近”入口清理。
- **后续设想**：地图摘要预览、首页动态地点卡片、摘要质量仪表盘和真实校园试点；这些能力只能消费已批准版本。

## 3. AI 地点摘要 V1 规格

### 3.1 地点详情顺序

地点详情统一按以下顺序展示：

1. 地点名称与核验状态；
2. 已审核稳定资料；
3. AI“此刻摘要”；
4. 可信层级、整理时间、来源数量；
5. 每条结论的“查看依据”来源卡片；
6. 冲突或证据不足提示；
7. 相关帖子；
8. 评分与评价；
9. “补充地点资料”入口。

所有示例均标记为**目标界面示意**。地图摘要预览和首页动态地点卡片在 P4，仅读取已批准摘要，不触发访问时生成。

### 3.2 输入来源与过滤

- 只读取当前学校、当前地点的数据。
- 动态帖子必须是 `published`、未删除、未过期，最多取最近 7 天 20 条。
- 评价必须是已发布、未删除，最多取最近 30 天 20 条。
- 被证伪数高于证实数的帖子不作为支持证据。
- 稳定资料只使用当前 `location_facts` 中已审核且有效的记录。
- 生成前将地点、资料、帖子和评价组成不可变输入快照，并保存快照哈希。

### 3.3 证据门槛与输出

- 动态结论至少需要两个不同用户的独立来源；不足时只返回空状态，不写具体结论。
- AI 返回的每个来源 ID 必须属于输入快照；出现虚构来源，整次生成失败。
- 相互矛盾的内容进入 `conflicts`，模型不得自行选择一方作为事实。
- 可信层级由服务端依据来源数量、时间和验证数据计算，模型不能自行判定。
- 每条结论保存 `claim_id`、正文、可信层级和来源引用；正文最多 300 字，摘要正文最多 1,200 字。

### 3.4 审核与发布

1. worker 生成 `pending_review` 版本；不直接替换当前摘要。
2. 管理员审核时必须同时查看摘要正文、每条结论、原始来源和冲突信息。
3. 批准后将地点的当前摘要引用切换到新版本，旧版本变为 `archived`。
4. 驳回写入审核意见，不替换旧版本；AI 失败或待审超时同样保留旧版本。
5. 没有已批准版本时展示证据不足空状态，并继续展示稳定资料和相关帖子。

## 4. 数据、接口和刷新机制

### 4.1 稳定资料数据模型

`location_facts` 保存已审核事实：

- `location_id`、`school_id`；
- `fact_key`：`normal_hours/services/price_note/contact/access/booking/other`；
- `label`、`value`、`sort_order`、`source_note`；
- `approved_by`、`approved_at`、`is_active`、`updated_at`。

`location_fact_proposals` 保存用户整批提议：

- 仅校园认证用户可以提交；
- 每份提议包含 `upserts`、`remove_keys` 和补充说明；
- 同一用户、同一地点最多一份待审核提议；
- 管理员整份批准或驳回，V1 不支持部分批准；
- 批准后更新稳定资料并标记该地点摘要 dirty；删除提议仍保留审核记录。

接口：

```text
POST /locations/{id}/fact-proposals
GET  /me/location-fact-proposals
GET  /admin/location-fact-proposals
POST /admin/location-fact-proposals/{id}/approve
POST /admin/location-fact-proposals/{id}/reject
```

### 4.2 AI 摘要版本

`location_summary_versions` 保存每次生成结果：

- 状态：`pending_review/approved/rejected/failed/archived`；
- 摘要正文、可信层级、结构化结论、冲突信息；
- 每条结论对应帖子、评价或稳定资料来源；
- 来源快照哈希、生成时间、失效时间、AI 调用日志 ID；
- 审核人、审核时间、审核意见和版本号。

`locations` 增加当前已批准摘要引用 `current_summary_id` 与刷新标记 `summary_dirty_at`。

接口：

```text
GET  /locations/{id}                       # 扩展稳定资料和已批准摘要概览
GET  /locations/{id}/summary               # 结论、冲突和可追溯来源卡片
GET  /admin/location-summaries?status=pending_review
POST /admin/location-summaries/{id}/approve
POST /admin/location-summaries/{id}/reject
POST /admin/locations/{id}/summary/refresh
```

### 4.3 刷新、租户与失败回退

- 帖子发布、编辑、过期、归档、地点变更、协同验证变化、评价变化或地点资料获批时标记 dirty。
- 新 worker 定期处理 dirty 地点，复用现有 AI Provider、调用日志和任务记录。
- 相同来源快照不重复生成；来源变化才产生新版本。
- 所有查询按 `school_id` 隔离；管理员操作先校验租户资源。
- 版本和审核记录永久保留，公开端只读当前已批准版本。
- AI 失败、生成结果不合规、驳回或新版本待审时，继续展示最近一次已批准版本；从未批准过则展示空状态。

## 5. 开发顺序

### P0：边界与口径清理

- 删除 `/locations/nearby`、Haversine、`distance` 字段、Web/小程序 `getNearby`、距离类型、`nearest` 排序、定位授权和“离我多远”文案。
- 保留静态地图、地点坐标、地点标记和帖子地点关联。
- 将旧方案标为废弃，修正认证方式和“已实现/待开发”标识。

### P1：地点资料提议与审核

- 完成两张资料表、迁移、跨校隔离、重复待审限制和管理员整批审核事务。
- Web、小程序地点详情增加稳定资料和补充入口。
- 管理员地点页增加“资料提议”队列。

### P2：AI 摘要、证据与审核

- 完成来源快照、证据过滤、冲突输出、虚构来源拒绝、可信层级计算和版本表。
- 接入 dirty worker、调用日志、任务记录和失败回退。
- 管理员地点页增加“AI 摘要待审”队列，审核时展示原始来源。

### P3：地点详情闭环

- Web 和小程序统一详情顺序、空状态、冲突提示、来源卡片和旧摘要回退。
- 相关帖子、评分评价保留原有能力，不能绕过审核直接生成摘要。

### P4：地图与首页消费

- 地图摘要预览和首页动态地点卡片只读取已批准摘要。
- 无摘要时展示地点资料和相关帖子，不在访问时生成。

## 6. 测试、验收与真实试点

### 6.1 自动化测试

- 后端：资料提议权限、审核事务、跨校隔离、重复待审限制、驳回和删除提议。
- Mock AI：来源过滤、证据门槛、冲突输出、虚构来源拒绝、调用失败回退。
- 版本状态：生成必为待审，批准才生效，驳回不替换旧版本。
- 刷新机制：所有触发事件标记 dirty，相同来源快照不重复调用。
- 旧版本：新版本待审或 AI 故障时仍可正常读取旧摘要。
- 边界清理：旧附近接口不可访问，代码和有效文档中不再存在定位、距离或 `nearest` 产品入口。
- Web 执行 `npm run build`；后端使用 `backend/.venv` 执行 `pytest tests/ -v`；小程序完成类型检查与编译。

### 6.2 端到端链路

跑通并记录以下链路：

```text
认证用户提交地点资料
→ 管理员批准
→ 来源发生变化
→ worker 生成 pending_review 摘要
→ 管理员核对每条来源并批准
→ Web/小程序查看摘要与原始依据
```

### 6.3 量化验收指标

| 指标 | 目标 |
| --- | --- |
| 摘要结论来源可追溯率 | 100%，每条结论均能打开输入快照中的来源 |
| 证据不足时具体结论数 | 0 |
| 跨校数据泄漏 | 0 |
| 未经管理员批准的摘要公开数 | 0 |
| 相同来源快照重复 AI 调用 | 0 |
| 旧摘要在待审/失败期间可读 | 100% |

### 6.4 真实试点

先在江南大学单校试点，选择食堂、打印店、图书馆等 10 个地点，连续观察 2 周：资料提议通过率、摘要审核退回率、来源缺失率、冲突率、用户查看来源的比例和摘要过期后的回退成功率。确认指标稳定后，再扩展到 fudan/zju 多租户演示学校。
