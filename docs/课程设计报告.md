## 1. 系统概述

"此刻校园"（Moment Campus）是一个面向大学校园的信息共享与沉淀平台。校园中存在大量真实、有用却容易消失的信息——哪个食堂窗口今天供应特色菜、哪家打印店更便宜、哪里适合自习、哪里经常出现校园小猫——这些信息分散在微信群、QQ 群、朋友圈和口口相传中，发布得快，消失得也快。

本系统通过"地点 + 时间 + 分类 + 标签 + 有效期"组织校园信息，让校园信息变得可搜索、可浏览、可验证、可更新、可收藏、可长期沉淀。它不是传统校园论坛，也不是普通社交平台，而是一张由校园成员共同维护的"校园生活地图"。

系统以 **江南大学蠡湖校区**为模拟核心（中心坐标 31.4837, 120.2712，地图缩放级别 16），面向学生、教职工、管理员三类用户提供校园生活信息的发布、浏览、地图发现、协同验证、订阅与协同维护服务。典型信息覆盖校园美食、校园动物、打印服务、学习资源、校园活动、校园设施、失物招领、校园兼职等 12 个分类。

本系统采用 B/S 架构，技术栈如下：

- **前端**：React + TypeScript + Vite + Tailwind CSS + MapLibre GL JS
- **后端**：Python + FastAPI + SQLAlchemy 2.0（async）+ asyncpg
- **数据库**：openGauss 7.0.0-RC3 轻量版（Docker 部署，唯一数据库）

系统的核心特性体现在四个方面：①openGauss 物理模型深度落地，包含 4 个表空间、66 个索引、8 个存储过程、8 个触发器、4 个物化视图、7 张分区表；②信息生命周期采用 6 态状态机（draft/pending/published/expired/conflict/archived）与 13 条合法流转规则；③社区治理采用 5 类协同验证（证实/证伪/补充更新/过期上报/冲突上报）；④基于 RBAC 的三级角色权限矩阵（user < admin < super_admin）。项目按 MVP 原则交付，172 项自动化测试全部通过。

## 2. 数据库设计各阶段书面文档

数据库设计严格遵循"需求分析 → 概念设计 → 逻辑设计 → 物理设计"四阶段方法论，各阶段产出与设计理由如下。

**需求分析阶段**：通过对江南大学学生、社团负责人、食堂管理员、图书馆管理员等的模拟访谈，结合问卷法、观察法与文献法，识别出 8 类用户痛点（信息分散、缺乏过期机制、信息矛盾、无人维护、历史无法追溯、无法按地点发现、难以判断可信度、变化无通知），并据此提炼出 26 项需求（普通用户 13 项、管理员 8 项、系统需求 5 项）。设计理由：痛点驱动需求，确保每个数据库实体都有真实业务来源，避免"为设计而设计"。

**概念设计阶段**：采用 E-R 模型，从需求分析的数据字典中识别出 21 个实体、35 个联系（1:N×30、M:N×2、自引用×1），并归纳为用户、信息、地图、互动、治理、管理 6 大功能模块。设计理由：以 Post（信息）为核心实体，承载主要业务流转；多对多联系通过关联实体（PostTag、TopicCollectionPost）实现；评论采用自引用支持回复树。

**逻辑设计阶段**：将 E-R 图转换为 21 张关系模式，全部规范化至第三范式（3NF），消除传递依赖；针对不同角色设计 15 个视图（11 个普通视图 + 4 个物化视图）。设计理由：3NF 保证数据无冗余；视图实现数据安全（隐藏敏感字段）与查询简化（预聚合统计）。

**物理设计阶段**：在 openGauss 7.0.0-RC3 轻量版上落实存储结构，设计 4 个表空间分离 I/O、66 个索引优化访问、8 个存储过程封装原子业务、8 个触发器实现自动化、4 个物化视图缓存聚合结果、7 张大表按时间 RANGE 分区。设计理由：OLTP 为主兼顾少量 OLAP，按访问模式选择 Astore/Ustore 双引擎与行存/列存，用部分索引与物化视图应对性能瓶颈。

## 4. 系统需求分析

### 4.1 用户痛点

通过对江南大学校园信息获取行为的调研，归纳出 8 类核心痛点，如表 4-1 所示。

表 4-1 用户痛点清单

| 编号 | 痛点 | 严重程度 | 出现场景 |
| ---- | ---- | -------- | -------- |
| P1 | 信息分散在群聊中，难以查找 | 高 | 找食堂今日菜单需翻多个群 |
| P2 | 信息时效性强但缺乏过期机制 | 高 | 看到旧信息以为图书馆还有座位 |
| P3 | 同一地点信息相互矛盾，难以判断 | 中 | 不同群友对同一窗口评价相反 |
| P4 | 信息发布后无人维护更新 | 高 | 维修公告维修完仍显示维修中 |
| P5 | 历史信息被覆盖后无法追溯 | 中 | 想查上周某活动是否举办 |
| P6 | 无法按地点快速发现附近信息 | 高 | 在图书馆附近想知道周边情况 |
| P7 | 难以判断信息是否可信 | 中 | 不确定某兼职信息是否真实 |
| P8 | 重要信息变化无通知 | 中 | 订阅的食堂窗口换菜不知道 |

上述痛点直接催生了系统的三大核心机制：6 态状态机（解决 P2/P4 过期与维护）、5 类协同验证（解决 P3/P7 矛盾与可信度）、地图维度发现（解决 P6 按地点发现）。

### 4.2 组织机构图

平台运营组织分为系统管理员组、内容运营组、用户支持组三支，下设超级管理员、普通管理员、审核员、编辑员、客服员、社区运营等岗位。校园信息来源则来自学生群体（本科生/研究生/留学生）、教职工群体（辅导员/任课教师/行政人员）、校园商户（食堂窗口/打印店/快递站/超市）与校园部门（学生工作处/图书馆/后勤处/保卫处）。平台与用户角色关系为三级：普通用户（信息发布者/浏览者/协同验证者/评论参与者）、管理员（内容审核/举报处理/置顶推荐/用户管理）、超级管理员（系统配置/权限分配/日志审计/数据初始化）。

### 4.3 数据流图

系统顶层数据流图（0 层上下文图）描述普通用户、管理员、外部地图 API、文件存储四个外部实体与平台系统之间的数据交互：用户向系统提交注册/登录凭证、发布内容、验证意见、评论、点赞、收藏、举报、搜索关键词、订阅请求；系统返回信息列表、详情、通知、搜索结果、信誉分与操作反馈；管理员向系统发送审核指令、举报处理指令、封禁指令、置顶推荐指令；外部地图 API 提供瓦片与坐标定位，文件存储承载图片上传。

第 0 层 DFD 将系统分解为 8 个主要处理过程：P1 用户认证、P2 信息发布、P3 信息浏览、P4 协同验证、P5 搜索推荐、P6 通知推送、P7 可信度计算、P8 内容管理。其中 P2 信息发布展开为草稿保存→信息校验→信息入库→状态置 pending→通知生成五个子过程；P4 协同验证展开为验证类型判断→写入验证记录→更新统计字段→触发可信度计算→更新信誉分→通知发布者六个子过程。

信息状态流转采用判定表约束，如表 4-2 所示（行为新状态，—表示不允许）。

### 4.5 数据字典

数据字典包含数据项、数据结构、数据流、数据存储与处理过程五部分。核心数据项 22 项（如 user_id、email、status、credibility_score、latitude、longitude、validation_type 等）；数据结构 6 项（用户、学校、信息、地点、验证记录、通知）；数据流 15 条；数据存储 21 项（与 21 张物理表一一对应）；处理过程 8 个（P1~P8）。其中 `latitude`/`longitude` 采用 `Numeric(10,7)`，精度约 1cm，满足校园级地图定位需求；`validation_type` 取值限定为 5 类协同验证类型；`status` 取值限定为 6 态状态机。

## 5. 功能需求分析与 E-R 图说明

### 5.1 功能需求分析

系统功能划分为 6 大模块、30 余项子功能。普通用户需求 13 项（P0×9，P1×4），覆盖注册登录、地图浏览、分类搜索、信息发布、协同验证、评论点赞收藏、举报、通知、历史、订阅、信誉分、草稿等；管理员需求 8 项，覆盖审核、举报处理、分类标签地点管理、用户封禁、置顶推荐、专题合集、操作日志、冲突裁定；系统需求 5 项，覆盖可信度计算、自动过期、冲突检测、版本管理、信誉分调整。

### 5.2 E-R 图说明

由于最终报告将转为 Word，此处采用文字描述实体及其联系（实际报告中可用 draw.io/Visio 重绘）。

**总体 E-R 图**：以 School（学校）、User（用户）、Post（信息）为核心。School 与 User、Post、Location、TopicCollection 均为 1:N 联系；User 与 Post 为 1:N（发布）；Post 与 Category、PostType、Location 为 N:1；Post 与 Comment、Like、Favorite、ValidationRecord、PostImage、Report 为 1:N；Post 与 Tag 为 M:N（通过 PostTag 关联实体）；Post 与 TopicCollection 为 M:N（通过 TopicCollectionPost 关联实体）；Comment 自引用（parent_id）实现评论回复树。

**用户子系统 E-R 图**：User 为中心，向外辐射出 Notification（user_id 接收者、actor_id 触发者，双角色引用）、TopicCollection（creator_id）、AdminOperationLog（admin_id）、Draft、BrowseHistory、SearchHistory，以及 Post、Comment、Like、Favorite、ValidationRecord、Report（reporter_id + handler_id 双角色）。

**信息子系统 E-R 图**：Post 关联 Category、PostType、Location 三个 N:1 外键，并向下展开 PostImage、Comment（自引用）、ValidationRecord 三个 1:N，以及 PostTag、TopicCollectionPost 两个 M:N 关联实体。

**互动与治理子系统 E-R 图**：User 与 Post、Comment 通过 Report 实体建立举报关系（可举报信息或评论），Notification 汇聚评论、点赞、收藏、验证、举报处理等事件触发。

**E-R 图设计要点**：①Post 为核心实体，与 12 个其他实体有联系，承载主要业务；②多对多联系通过关联实体实现，避免冗余外键；③Comment 自引用支持回复树；④核心业务实体采用 `is_deleted + deleted_at` 软删除；⑤Post.status 与 TopicCollection.status 实现状态流转；⑥Report 与 Notification 采用双角色外键引用。

## 6. 系统设计

### 6.1 概念设计

概念设计识别出 21 个实体（E01~E21）：School、User、Category、PostType、Location、Tag、Post、PostTag、PostImage、Comment、Like、Favorite、ValidationRecord、Report、Notification、TopicCollection、TopicCollectionPost、Draft、BrowseHistory、SearchHistory、AdminOperationLog。实体间联系 35 个，其中 1:N 联系 30 个、M:N 联系 2 个、自引用 1 个。Post 实体属性最为丰富，含 user_id、school_id、category_id、post_type_id、location_id 五个外键，以及 title、content、status、credibility_score、view_count、like_count、comment_count、favorite_count、valid_count、invalid_count、expire_at、activity_start_at/end_at、lost_type、contact_info、is_top、is_recommend 等业务字段。

### 6.2 模块设计

系统功能模块总图分为 6 大模块：

- **用户模块**：注册登录、个人资料、权限管理、信誉管理、浏览历史、搜索历史。
- **信息模块**：信息发布、信息浏览、信息搜索、信息详情、草稿管理、版本历史。
- **地图模块**：地图浏览、地点标记、地点筛选、地点导航、状态展示。
- **互动模块**：评论回复、点赞、收藏、通知推送、地点订阅。
- **治理模块**（核心）：协同验证（5 类）、举报处理（5 类）、可信度计算、冲突检测、自动过期、版本管理、信誉调整。
- **管理模块**：内容审核、用户管理、分类标签、地点管理、置顶推荐、专题合集、操作日志、冲突裁定。

表 6-1 治理模块协同验证子功能

| 子功能 | 输入 | 输出 | 涉及实体 |
| ------ | ---- | ---- | -------- |
| 协同验证 | post_id, type | validation_id | ValidationRecord, Post |
| 举报处理 | report_id | result | Report, AdminOperationLog |
| 可信度计算 | post_id | score | Post, ValidationRecord, User |
| 冲突检测 | location_id | conflict_list | Post, ValidationRecord |
| 自动过期 | time | expired_list | Post, Category |

### 6.3 逻辑结构设计

逻辑设计将 E-R 图转换为 21 张关系模式，全部满足 3NF。主键统一为 `id`（BIGINT 自增），外键命名遵循 `<被引用实体>_id` 规范，软删除统一为 `is_deleted + deleted_at`，时间戳为 `created_at + updated_at`。统计结果如表 6-2 所示。

表 6-2 关系模式统计

| 统计项 | 数量 |
| ------ | ---- |
| 关系模式（表） | 21 |
| 主键 | 21（全部为 id） |
| 外键 | 35 |
| 唯一约束 | 8 |
| 软删除字段表 | 12 |
| 状态字段表 | 4（posts/comments/reports/topic_collections） |

以核心表 posts 为例，其关系模式定义为：

```
posts (id PK, user_id FK→users, school_id FK→schools, category_id FK→categories,
       post_type_id FK→post_types, location_id FK→locations(可空),
       title, content, is_anonymous, status(6态), credibility_score,
       view_count, like_count, comment_count, favorite_count,
       valid_count, invalid_count, expire_at, activity_start_at, activity_end_at,
       lost_type, contact_info, is_top, is_recommend,
       created_at, updated_at, is_deleted, deleted_at)
```

完整性约束方面：实体完整性由 PRIMARY KEY 保证；参照完整性由 FOREIGN KEY + `ON DELETE RESTRICT` 保证；用户定义完整性包括 email 唯一、role 枚举（user/admin/super_admin）、status 枚举（6 态）、validation_type 枚举（5 类）、report_type 枚举（5 类）、likes 与 favorites 的联合唯一约束、经纬度范围约束等。

**视图设计**：针对不同角色设计 15 个视图，按权限分级访问。普通视图 11 个（如 v_published_posts 已发布信息视图、v_post_detail 详情视图、v_user_profile 公开信息视图、v_my_posts 我的信息视图、v_pending_review_posts 待审核视图等）；物化视图 4 个（v_post_validation_stats 验证统计、v_user_reputation_ranking 信誉排行、v_admin_dashboard 仪表盘、v_location_post_count 地点统计）。视图权限矩阵实现了"未登录用户可见公开视图、登录用户可见个人信息、管理员可见审核与治理视图、超级管理员可见完整视图"的分级安全控制。

### 6.4 物理结构设计

### 7.3 状态流转接口（后端）

状态流转由后端 `POST /posts/{id}/transition` 接口实现，是 6 态状态机的服务层入口。接口首先调用 `can_transition()` 校验流转合法性，再按 RBAC 权限校验：普通用户仅可将自己的草稿提交审核（draft→pending）或放弃草稿（draft→archived），管理员可执行所有合法流转（审核通过/驳回/归档/过期/冲突标记等），archived 为终态不可流转。

```python
@router.post("/{post_id}/transition", response_model=PostTransitionResponse)
async def transition_post_status(post_id: int, data: PostTransitionCreate,
        current_user: User = Depends(get_current_user), db: AsyncSession = Depends(get_db)):
    post = (await db.execute(select(Post).where(Post.id == post_id, Post.is_deleted == False))).scalar_one_or_none()
    if not post: raise NotFoundException(detail="信息不存在")
    previous_status = post.status
    target = normalize_status(data.target_status)
    if not can_transition(previous_status, target):
        raise BadRequestException(detail=f"非法状态流转：{previous_status} → {target}")
    is_admin = _is_admin(current_user); is_owner = post.user_id == current_user.id
    user_allowed = is_owner and previous_status == PostStatus.DRAFT and target in {PostStatus.PENDING, PostStatus.ARCHIVED}
    if not is_admin and not user_allowed:
        raise ForbiddenException(detail="无权限执行此状态流转")
    post.status = target; post.updated_at = datetime.now()
    await db.commit()
    return PostTransitionResponse(post_id=post.id, previous_status=previous_status, current_status=post.status,
        transitioned_at=post.updated_at, transitioned_by=current_user.id)
```

### 7.4 协同验证接口（后端）

协同验证由 `POST /posts/{id}/validate` 与 `GET /posts/{id}/validation-stats` 两个接口实现。提交接口将验证类型归一化（兼容旧别名 valid→confirmation、invalid→refutation、uncertain→update）后写入 validation_records，并同步更新 Post 的 valid_count/invalid_count 兼容字段。统计接口按 validation_type 分组计数，返回 5 类细分计数、旧 3 类兼容字段与综合有效性状态。

```python
@router.post("/posts/{post_id}/validate", response_model=ValidationResponse)
async def create_validation(post_id: int, data: ValidationCreate,
        current_user: User = Depends(get_current_user), db: AsyncSession = Depends(get_db)):
    post = (await db.execute(select(Post).where(Post.id == post_id, Post.is_deleted == False))).scalar_one_or_none()
    if not post: raise NotFoundException(detail="帖子不存在")
    canonical_type = normalize_validation_type(data.validation_type)  # 别名 → 正式名
    validation = ValidationRecord(post_id=post_id, user_id=current_user.id,
                                  validation_type=canonical_type, comment=data.comment)
    db.add(validation)
    if canonical_type in ValidationType.LEGACY_POSITIVE_COUNT_TYPES: post.valid_count += 1
    elif canonical_type in ValidationType.LEGACY_NEGATIVE_COUNT_TYPES: post.invalid_count += 1
    await db.commit()
    return ValidationResponse(id=validation.id, post_id=validation.post_id, user_id=validation.user_id,
        validation_type=validation.validation_type, comment=validation.comment, created_at=validation.created_at)
```

### 9.1 开发收获

通过本次课程设计，我系统实践了数据库设计四阶段方法论，从需求分析、概念设计、逻辑设计到物理设计完整走通了一遍。在 openGauss 这一国产数据库上深度应用了表空间、分区表、存储过程、触发器、物化视图、部分索引、GIN 索引等高级特性，对"逻辑模型与物理模型解耦""按访问模式选择存储引擎"有了切身体会。同时掌握了 FastAPI 异步后端、SQLAlchemy 2.0 async ORM、React + TypeScript 前端的现代全栈开发模式，以及 pytest 异步测试方法。

### 9.2 遇到的问题及解决方法

**问题一：openGauss 与 SQLite 类型不一致。** 原 Base 项目主键为 Integer、外键为 BigInteger，存在类型不一致问题，迁移到 openGauss 后统一为 BIGINT。解决方法是在 SQLAlchemy 模型中使用 `BigInteger().with_variant(Integer, "sqlite")` 兼容写法，并在物理模型层统一为 BIGINT。

**问题二：openGauss PGXC 架构不支持 `TRUNCATE ... RESTART IDENTITY`。** 测试与 seed 脚本清空数据后自增序列无法自动重置。解决方法是显式调用 `setval(pg_get_serial_sequence(...), 1, false)` 或 `ALTER SEQUENCE <table>_id_seq RESTART WITH 1` 手动重置。

**问题三：分区表对部分索引（partial index）有限制。** openGauss 分区表上部分表达式索引与部分索引受限。解决方法是将受限索引调整为全局索引，或在子表上单独创建，详见 SQL 脚本注释。

**问题四：6 态状态机与旧 3 态数据的兼容。** 文档中使用 `pending_review` 而代码使用 `pending`，旧验证数据使用 valid/invalid/uncertain 而新设计为 5 类。解决方法是引入别名映射（ALIASES）与归一化函数（normalize_status / normalize_validation_type），读取历史数据时自动归一化，写入时统一存储正式名。

**问题五：物理层存储过程已就绪但应用层未联动。** 可信度计算、自动过期、冲突检测等存储过程已在数据库实现，但应用层未调用。按 MVP 原则，这部分作为后续演进项，报告与 TODO 中如实记录为未完成，未将未完成内容写成已完成。

### A.1 6 态状态机定义（backend/app/core/post_status.py）

```python
class PostStatus:
    DRAFT = "draft"
    PENDING = "pending"            # 待审核（文档记为 pending_review）
    PUBLISHED = "published"
    EXPIRED = "expired"
    CONFLICT = "conflict"
    ARCHIVED = "archived"

    ALL: tuple = (DRAFT, PENDING, PUBLISHED, EXPIRED, CONFLICT, ARCHIVED)
    ALIASES: dict = {"pending_review": PENDING}

# 合法流转规则：current -> {allowed target statuses}
# draft→{pending,archived}; pending→{published,draft,archived};
# published→{expired,conflict,archived}; expired→{published,archived};
# conflict→{published,archived}; archived→{}（终态）
# 除 archived 终态外共 12 条流转路径，连同 archived 终态约束合计 13 条合法流转规则。
_TRANSITIONS: dict = {
    PostStatus.DRAFT:     {PostStatus.PENDING, PostStatus.ARCHIVED},
    PostStatus.PENDING:   {PostStatus.PUBLISHED, PostStatus.DRAFT, PostStatus.ARCHIVED},
    PostStatus.PUBLISHED: {PostStatus.EXPIRED, PostStatus.CONFLICT, PostStatus.ARCHIVED},
    PostStatus.EXPIRED:   {PostStatus.PUBLISHED, PostStatus.ARCHIVED},
    PostStatus.CONFLICT:  {PostStatus.PUBLISHED, PostStatus.ARCHIVED},
    PostStatus.ARCHIVED:  set(),  # 终态
}

def can_transition(current: str, target: str) -> bool:
    current = normalize_status(current)
    target = normalize_status(target)
    return target in _TRANSITIONS.get(current, set())

def get_allowed_transitions(current: str) -> Set[str]:
    current = normalize_status(current)
    return _TRANSITIONS.get(current, set()).copy()
```

### A.2 5 类协同验证类型定义（backend/app/core/validation_type.py）

```python
class ValidationType:
    CONFIRMATION = "confirmation"            # 证实
    REFUTATION = "refutation"                # 证伪
    UPDATE = "update"                        # 补充更新
    EXPIRATION_REPORT = "expiration_report"  # 过期上报
    CONFLICT_REPORT = "conflict_report"      # 冲突上报

    ALL: tuple = (CONFIRMATION, REFUTATION, UPDATE, EXPIRATION_REPORT, CONFLICT_REPORT)
    # 向后兼容旧 3 类
    ALIASES: dict = {"valid": CONFIRMATION, "invalid": REFUTATION, "uncertain": UPDATE}
    LEGACY_POSITIVE_COUNT_TYPES: Set[str] = {CONFIRMATION}
    LEGACY_NEGATIVE_COUNT_TYPES: Set[str] = {REFUTATION}

def normalize_validation_type(vtype: str) -> str:
    return ValidationType.ALIASES.get(vtype, vtype)
```

### A.3 RBAC 权限矩阵（backend/app/core/permissions.py）

```python
class Role:
    USER = "user"
    ADMIN = "admin"
    SUPER_ADMIN = "super_admin"

# 角色层级：数值越大权限越高，高级角色自动包含低级角色全部权限
ROLE_LEVEL: dict[str, int] = {Role.USER: 1, Role.ADMIN: 2, Role.SUPER_ADMIN: 3}

def has_role(user: User | None, required_role: str) -> bool:
    if user is None: return False
    return get_role_level(user.role) >= ROLE_LEVEL.get(required_role, ROLE_LEVEL[Role.USER])

def require_role(required_role: str) -> Callable:
    from app.dependencies import get_current_user
    async def _check_role(user: User = Depends(get_current_user)) -> User:
        if not has_role(user, required_role):
            raise ForbiddenException(detail=f"没有权限执行此操作，需要 {required_role} 及以上角色")
        return user
    return _check_role
```

### A.4 可信度重算存储过程（openGauss PL/pgSQL）

```sql
CREATE OR REPLACE FUNCTION sp_recalc_credibility(p_post_id BIGINT)
RETURNS NUMERIC(5,2) AS $$
DECLARE
    v_confirm_cnt INTEGER; v_refute_cnt INTEGER; v_update_cnt INTEGER;
    v_expire_cnt INTEGER; v_conflict_cnt INTEGER;
    v_credibility NUMERIC(5,2); v_author_rep NUMERIC(5,2);
BEGIN
    SELECT COUNT(*) FILTER (WHERE validation_type = 'confirmation'),
           COUNT(*) FILTER (WHERE validation_type = 'refutation'),
           COUNT(*) FILTER (WHERE validation_type = 'update'),
           COUNT(*) FILTER (WHERE validation_type = 'expiration_report'),
           COUNT(*) FILTER (WHERE validation_type = 'conflict_report')
    INTO v_confirm_cnt, v_refute_cnt, v_update_cnt, v_expire_cnt, v_conflict_cnt
    FROM validation_records WHERE post_id = p_post_id AND is_deleted = FALSE;

    SELECT COALESCE(reputation_score, 60.00) INTO v_author_rep
    FROM users u JOIN posts p ON p.user_id = u.id WHERE p.id = p_post_id;

    -- 基础分 = 作者信誉*0.3 + 50*0.7；证实+5/条，证伪-8/条，更新+2/条，过期报告-10/条，冲突报告-15/条
    v_credibility := v_author_rep * 0.3 + 50.0 * 0.7
                   + v_confirm_cnt * 5.0 - v_refute_cnt * 8.0
                   + v_update_cnt * 2.0 - v_expire_cnt * 10.0 - v_conflict_cnt * 15.0;
    v_credibility := GREATEST(0.0, LEAST(100.0, v_credibility));

    UPDATE posts SET credibility_score = v_credibility, valid_count = v_confirm_cnt,
           invalid_count = v_refute_cnt, updated_at = CURRENT_TIMESTAMP
    WHERE id = p_post_id;
    RETURN v_credibility;
END;
$$ LANGUAGE plpgsql;
```

### A.5 评论计数触发器（openGauss PL/pgSQL）

```sql
CREATE OR REPLACE FUNCTION trg_func_comment_update_count()
RETURNS TRIGGER AS $$
BEGIN
    IF (TG_OP = 'INSERT') THEN
        UPDATE posts SET comment_count = comment_count + 1, updated_at = CURRENT_TIMESTAMP
        WHERE id = NEW.post_id;
        RETURN NEW;
    ELSIF (TG_OP = 'DELETE') THEN
        UPDATE posts SET comment_count = GREATEST(0, comment_count - 1), updated_at = CURRENT_TIMESTAMP
        WHERE id = OLD.post_id;
        RETURN OLD;
    END IF;
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_comment_insert_count AFTER INSERT ON comments
    FOR EACH ROW EXECUTE PROCEDURE trg_func_comment_update_count();
CREATE TRIGGER trg_comment_delete_count AFTER DELETE ON comments
    FOR EACH ROW EXECUTE PROCEDURE trg_func_comment_update_count();
```

```sql
CREATE OR REPLACE VIEW v_published_posts AS
SELECT p.id, p.title, p.content, p.is_anonymous, p.status, p.credibility_score,
       p.view_count, p.like_count, p.comment_count, p.favorite_count,
       p.valid_count, p.invalid_count, p.expire_at, p.is_top, p.is_recommend,
       p.created_at, p.updated_at,
       u.nickname AS author_nickname, u.avatar_url AS author_avatar,
       CASE WHEN p.is_anonymous = TRUE THEN NULL ELSE u.id END AS author_id,
       c.name AS category_name, c.icon AS category_icon,
       pt.name AS post_type_name, l.name AS location_name,
       l.latitude AS location_lat, l.longitude AS location_lng, s.name AS school_name
FROM posts p
    INNER JOIN users u ON p.user_id = u.id
    INNER JOIN categories c ON p.category_id = c.id
    INNER JOIN post_types pt ON p.post_type_id = pt.id
    INNER JOIN schools s ON p.school_id = s.id
    LEFT JOIN locations l ON p.location_id = l.id
WHERE p.status = 'published' AND p.is_deleted = FALSE;
```
