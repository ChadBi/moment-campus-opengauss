## 二、详细演示脚本

### 第一阶段：开场介绍（1分钟）

**操作：** 打开浏览器，访问 `https://campus.chaina1.com`

**讲解话术：**

> "各位老师好，我今天演示的项目是'此刻校园'——一个基于 openGauss 的校园信息共享与沉淀平台。
>
> 简单来说，这不是一个传统的校园论坛，而是一张由校园成员共同维护的'校园生活地图'。校园里有很多有用但容易消失的信息——比如哪个食堂窗口好吃、哪里适合自习、哪里有校园小猫——这些信息分散在微信群、朋友圈里，发得快消失得也快。我们的平台就是通过地点、时间、分类、标签和有效期来组织这些信息，让它们变得可搜索、可验证、可沉淀。
>
> 技术上，前端用的是 React + TypeScript，后端是 Python + FastAPI，数据库是 openGauss 7.0。我们以江南大学蠡湖校区为模拟场景进行演示。"

**展示要点：**
- 首页水墨风 UI 设计
- 江南大学信息
- 页面整体布局

---

### 第二阶段：数据库设计亮点（2分钟）

**操作：** 停留在首页，口头讲解数据库设计（或快速切换到 ER 图截图）

**讲解话术：**

> "在数据库设计方面，我们做了比较完整的设计：
>
> **整体规模**：21 张表，分为 5 大子系统——用户子系统、信息子系统、互动子系统、治理子系统和管理子系统。
>
> **openGauss 深度应用**：
> - 4 个表空间：按业务类型分离存储（系统表空间、核心业务表空间、互动表空间、日志表空间）
> - 7 张分区表：对帖子、评论、通知等大表按时间做 RANGE 分区
> - 8 个存储过程和 8 个触发器：实现业务自动化，比如计数器更新、软删除级联、操作日志记录
> - 4 个物化视图：加速管理员仪表盘的统计查询
> - 66 个索引：包括 8 个部分索引，针对常见查询场景优化
>
> **业务特色设计**：
> - 6 态状态机：草稿→待审核→已发布→争议/过期→归档，共 13 条合法流转路径
> - 2 类协同验证：证实、证伪；每用户每帖一票，可切换或取消
> - 独立自动过期任务：systemd timer 在系统启动后 5 分钟首次触发 oneshot worker，此后每 30 分钟触发一次
> - RBAC 三级权限：普通用户、管理员、超级管理员，权限向下兼容
>
> 接下来我给大家演示系统的实际功能。"

### 第三阶段：系统功能演示（8-10分钟）

#### 场景一：游客浏览（1分钟）

**操作路径：**
1. 首页展示信息流
2. 点击顶部由当前学校 API 动态加载的分类标签切换
3. 点击一条信息进入详情页
4. 向下滚动查看评论区

**讲解话术：**

> "首先是游客视角，不需要登录就能浏览信息。首页是信息流，展示校园里的各种信息。顶部可以按分类筛选，每条信息都关联了地点、标签和有效期。
>
> 点进去看详情页，我们用了长卷式的布局设计，信息内容、作者信息、地点、验证状态、评论区都在一个页面里。"

**展示要点：**
- 水墨风 UI 特色
- 分类筛选功能
- 信息卡片布局
- 详情页长卷式设计

#### 场景二：地图发现（1分钟）

**操作路径：**
1. 点击左侧导航栏"地图"
2. 等待地图加载（江南大学蠡湖校区）

**讲解话术：**

**展示要点：**
- 地图加载与交互

#### 场景四：互动与协同验证（2分钟）

**操作路径：**
1. 在刚发布的详情页（或任意一条信息）
2. 点击"点赞"按钮（心形图标）
3. 向下滚动到评论区，发表一条评论（如"看起来不错，下次去试试"）
4. 回到信息主体部分，找到"有效性确认"区域
5. 点击"确认有效"（或有效性确认按钮）
6. 点击“证实”，展示计数变化
7. 切换为“证伪”，展示两类计数同步变化
8. 再次点击“证伪”取消验证
9. 点击左上角头像或用户名，进入个人中心
10. 展示“我的发布”

**讲解话术：**

> "除了浏览和发布，用户还可以通过点赞和评论参与互动。
>
> 我们重点说一下'协同验证'——这是平台的核心机制。用户可以对一条信息选择证实或证伪，两类互斥，可以切换，再次点击同类即可取消。
>
> 为什么要做这个？因为校园信息的时效性很强，而且真假难辨。社区验证提供事实判断统计；时间到期由独立 systemd timer 触发 worker，按 6 态状态机自动转为过期，不依赖 Web 进程内调度。
>
> 这些互动数据会沉淀在帖子详情和个人中心里，方便后续回看发布与参与记录。"

**展示要点：**
- 点赞、评论基础互动
- 2 类互斥协同验证机制（重点讲解）
- 验证计数的实时变化
- 个人中心的发布记录

**展示要点：**

## 四、常见问题与回答准备

### Q1：为什么选择 openGauss？

> "首先是课程要求，其次 openGauss 作为国产数据库，在功能上完全满足我们的需求，而且支持分区表、存储过程、触发器、物化视图这些高级特性，和 PostgreSQL 高度兼容，迁移成本也比较低。"

### Q2：性能怎么样？有没有做测试？

> "我们做了 8 个关键查询的性能测试，全部达标。比如帖子列表查询、搜索查询、地图标记查询，都是毫秒级响应。我们还做了索引优化、物化视图来提升查询性能。具体数据在测试报告里有记录。"

### Q3：数据量多大？

> "演示环境里有 11 个用户、30 多条帖子、若干评论和互动数据。物理模型设计支持的规模要大得多，分区表和索引设计都是按万级、十万级来考虑的。"

### Q4：遇到的最大挑战是什么？

> "最大的挑战是 openGauss 的适配。原项目是用 SQLite 的，迁移到 openGauss 遇到了一些兼容性问题，比如主键外键类型不匹配、SQL 方言差异等等。另外 openGauss 轻量版有一些限制，比如不支持中文分词扩展，我们也做了相应的调整。"

### Q5：前端 UI 是什么风格？

> "我们用了水墨风的设计语言，减少了过度的圆角和阴影，用了宣纸纹理和墨线分割，整体比较有中国风的感觉，也是想做出一点校园文化的特色。"

### Q6：项目架构是什么样的？

> "前后端分离架构。前端 React + TypeScript + Vite + Tailwind CSS，后端 Python + FastAPI + SQLAlchemy 异步模式，数据库 openGauss 7.0。部署在华为云 ARM 服务器上，Nginx 做反向代理，HTTPS 加密访问。"

## 五、应急方案

### 5.1 公网访问不了

- 快速切换到本地开发环境（提前启动好）
- 命令：`cd backend && .\.venv\Scripts\activate && uvicorn app.main:app --port 8000`
- 前端：`cd frontend && npm run dev`
- 访问：`http://localhost:5173`

### 5.2 某个功能出错

- 不要卡住，快速跳过，说"这个功能平时是好的，可能演示环境有点问题，后面可以再看"
- 继续下一个功能

### 5.3 网络卡顿

- 提前把关键页面打开在标签页里
- 切换标签页而不是等加载
